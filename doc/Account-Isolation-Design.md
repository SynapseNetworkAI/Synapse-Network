# A2A-Pay 账户与权限隔离设计方案

为了确保 A2A-Pay 系统的资金安全、管理权限清晰以及 Agent 自主交易风险可控，系统采取了**严格的账户与权限隔离机制**。

该设计主要分为两个维度：**Web 端管理角色的隔离 (Dashboard vs Admin)** 以及 **Web3 资金与执行层面的隔离 (Agent 客户端 vs 平台主账户)**。

---

## 1. 业务管理面板隔离 (Dashboard vs Admin)

此层隔离主要针对**Web 端使用者**的使用场景进行职权切割。

### 1.1 Dashboard 账户 (Agent Operator / 平台普通用户)
* **角色定位**：拥有并管理一支或多支 AI Agent 舰队的开发者或普通用户。
* **认证方式**：Web3 钱包直连 (如 MetaMask)。钱包地址即用户唯一身份标识（EOA）。
* **核心权限**：
  * 只允许查看与自己钱包地址关联的 Agent 节点数据。
  * 操作其专属 Agent 的创建、启停。
  * 对其名下的 Agent 钱包进行资金划拨（充值 Gas、USDC，或将 Agent 赚取的代币提取至当前主钱包）。
* **隔离策略**：数据层面的行级隔离 (Row-level Security)，无论是后端 Indexer 还是智能合约，只信任当前 `msg.sender` 的所属权。

### 1.2 Admin 账户 (Gods View / 系统管理员)
* **角色定位**：A2A-Pay 协议的运营方或核心开发者，负责全局安全与经济模型调控。
* **认证方式**：多重认证机制。
  1. **Web3 签名验证**：限定在白名单内的特定管理员 EOA 地址（如 `Deployer` 地址）。
  2. **Web2 动态验证**：集成 OTP (如 Google Authenticator / otplib) 进行二次前端页面与 API 路由的防绕过校验（`AdminGuard`）。
* **核心权限**：
  * 修改基础协议费率（Fee Rate）与收款地址（Treasury）。
  * 紧急情况下的全局断路器（Pause Protocol）。
  * 宏观业务数据监控（全局大盘流水，所有 Agent 活动情况）。
* **隔离策略**：
  * **不能代客理财**：系统管理员拥有系统层参数修改权，**但绝无权限移动甚至读取具体普通用户的 Agent 资金或私钥**，完全符合 Web3 非托管 (Non-custodial) 精神。

---

## 2. 资金执行切面隔离 (Agent 客户端 vs 平台户)

此层隔离关注的是**如何安全地赋予 AI Agent 支付能力**而不产生资金外逃风险。

### 2.1 平台用户主钱包 (Platform User Cold Wallet)
* **定位**：用户的外部主控钱包 (EOA)，例如用户的 MetaMask 或硬件钱包。
* **职能**：作为大额资金的“金库”（Cold/Voult Wallet）。
* **安全性**：私钥存在本地，绝不上链，绝不交给平台或 Agent 环境，只有在 Dashboard 页面主动点击确认（签名）授权时，才会产生资金流出。

### 2.2 Agent 客户端独立钱包 (Agent Smart/Hot Wallet)
* **定位**：专属于某一个 AI Agent 的受限执行钱包（通常为一个内置私钥的 EOA 或基于 EOA 驱动的智能合约钱包 `AgentSmartWallet`）。
* **职能**：作为“零钱包”负责机器与机器 (A2A) 之间高频、小额的免密即时结算。
* **隔离与约束机制**：
  * **私钥分离**：Agent 客户端（例如 Python 运行环境）运行在一个随机生成且只对其自身可见的私钥下，**不读取主钱包私钥**。
  * **权限降级设计**：Agent 自身的私钥**仅具备调用 `Escrow` 合约进行支付和签名的权限**。
  * **大额提现锁**：当 Agent 赚取了收益（如售卖数据获得 USDC），这些资产要么直接结算在 Escrow 的锁定逻辑中，要么结算到 `AgentSmartWallet` 合约内。而 **Agent 客户端私钥没有将大额资金向外转移至任意黑客地址的权限**，提取资金 (`withdraw`) 必须由绑定的**平台用户主钱包**去触发。

### 2.3 平台系统金库 (Protocol Treasury)
* **定位**：由 A2A-Pay Admin 控制的多签钱包。
* **职能**：独立接收系统产生的微额服务费手续费。不可用于支付具体的 Agent 节点消费。

---

## 3. 合约执行视角的授权模型 (Authorization Matrix)

通过系统内的智能合约架构，账户隔离最终在链上得到强制保障：

| 实体 (Entity) | 私钥控制方 | 可操作功能 (Contract Scope) | 提款权限 (Withdrawal) |
| :--- | :--- | :--- | :--- |
| **Admin Wallet** | 核心开发者 | 变更 `Escrow` 手续费, 合约升级 | 无权动用户资金, 仅能提现系统手续费 |
| **User Main Wallet** | 平台用户 | 管理专属 Agent, 存入资金, 提取资金 | 将对应 Agent 账户的余额无损提取回主钱包 |
| **Agent Wallet** | Agent 运行时环境 | 仅发起 API 购买请求, 签名支付凭证 | 无提现权限 (不可转移代币至无关地址) |

## 4. 总结与最佳实践
1. 前端采用**多端应用或隔离路由** (`/dashboard` vs `/admin`)，辅以独立的状态管理与二次动态密码 (`otplib` OTP) 的双因素控制。
2. 后端 Indexer 或 API 网关通过 JWT + `msg.sender` 进行严格的行列权限校验。
3. AI 终端采用 **“零钱包”+“授权额度 (Allowance)”** 模式运作，把用户大额资产被 AI 模型幻觉或被攻击者偷取的风险降到最低。
