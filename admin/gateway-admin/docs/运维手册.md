# gateway-admin 运维手册

## 1. 目录规划

建议把 `gateway-admin` 的运维相关文件固定在下面这套结构里：

```text
admin/gateway-admin/
├── docs/
│   ├── README.md
│   └── 运维手册.md
├── logs/
│   └── gateway-admin.log
├── run/
│   └── gateway-admin.pid
├── scripts/
│   └── ops/
│       ├── common.sh
│       ├── start-local.sh
│       ├── start-prod.sh
│       ├── stop.sh
│       ├── restart.sh
│       └── status.sh
├── .env.example
├── README.md
└── src/
```

说明：

- `scripts/ops/` 只放运维动作脚本，不掺杂测试或迁移脚本。
- `logs/` 放服务标准输出和错误输出。
- `run/` 放 PID 文件，避免把 PID 混在项目根目录。
- `docs/` 放运维说明和发布操作手册，不再散落在根 README。

### 2.2 环境变量

推荐在 `admin/gateway-admin/.env.local` 中维护本地或单机部署配置。

最小建议配置：

```bash
ADMIN_GATEWAY_HOST=0.0.0.0
ADMIN_GATEWAY_PORT=8300
ADMIN_GATEWAY_DEBUG=false
ADMIN_GATEWAY_ALLOWED_ORIGINS=http://localhost:3000,http://localhost:4000
ADMIN_GATEWAY_TOKEN_PREFIX=adm_demo_
ADMIN_SESSION_TTL_SEC=3600
ADMIN_SESSION_COOKIE_NAME=synapse_admin_session
ADMIN_SESSION_COOKIE_SECURE=false
ADMIN_SESSION_COOKIE_SAMESITE=lax
ADMIN_SESSION_COOKIE_DOMAIN=
ADMIN_CSRF_SECRET=replace-this-with-a-dedicated-admin-csrf-secret
ADMIN_GOOGLE_AUTHENTICATOR_LOGIN_ENABLED=true
ADMIN_GOOGLE_AUTHENTICATOR_HIGH_RISK_ENABLED=true
ADMIN_GOOGLE_AUTHENTICATOR_ISSUER=Synapse Gateway Admin
ADMIN_GOOGLE_AUTHENTICATOR_WINDOW=1
ADMIN_DATABASE_DSN=postgresql://synapse_admin_app:12345678@localhost:5432/synapse_gateway_admin
ADMIN_DATABASE_MIGRATION_DSN=postgresql://synapse:12345678@localhost:5432/synapse_gateway_admin
GATEWAY_READONLY_DSN=postgresql://synapse_gateway_ro:12345678@localhost:5432/synapse_gateway
GATEWAY_INTERNAL_BASE_URL=http://localhost:8000
GATEWAY_INTERNAL_ADMIN_WALLET=0xYourGatewayAdminWallet
GATEWAY_INTERNAL_JWT_SECRET=replace-this-with-a-32-byte-minimum-jwt-secret
GATEWAY_INTERNAL_TOKEN_ISSUER=gateway-admin
GATEWAY_INTERNAL_TOKEN_AUDIENCE=gateway-internal
GATEWAY_INTERNAL_SERVICE_SUBJECT=service:gateway-admin
EXECUTION_WORKER_ENABLED=true
EXECUTION_WORKER_POLL_INTERVAL_SEC=5
EXECUTION_WORKER_BATCH_SIZE=10
ADMIN_GATEWAY_USE_INMEMORY_STORE=false
```

说明：

- `ADMIN_CSRF_SECRET` 是 cookie 会话模式下的必配项；它决定 `/auth/login`、`/auth/me`、`/auth/mfa/enroll/verify` 返回的 `csrfToken` 是否能被前端后续写请求正确使用。
- `ADMIN_SESSION_COOKIE_*` 一组参数控制后台会话 cookie 的名字、域、Secure 和 SameSite 策略；如果这些值和实际域名/协议不匹配，就会出现“浏览器没带 cookie”或“CSRF token 无法建立”的假登录问题。
- `ADMIN_GOOGLE_AUTHENTICATOR_*` 一组参数控制登录 MFA、首绑二维码 issuer、高风险 step-up 策略；如果关闭 `ADMIN_GOOGLE_AUTHENTICATOR_LOGIN_ENABLED`，已绑定账号登录将不再要求 `otpCode`。
- `ADMIN_DATABASE_MIGRATION_DSN` 是旧库补表、补视图时的必配项之一；应用账号通常没有 schema `CREATE / ALTER` 权限。
- `GATEWAY_INTERNAL_TOKEN_*` 一组参数控制 admin -> gateway 内部 service token 的 `iss / aud / sub`，生产必须和 gateway 侧受信配置完全一致。
- `bootstrap` 管理员账号默认只有账号和角色，不内置明文初始密码。
- 首次启用前，需要显式给目标账号写入 `password_hash`。
- 当前登录校验是 `email + password + otpCode`；仅写邮箱或 OTP 不够。

### 2.2.1 Missing admin CSRF token 的真实含义

如果页面出现 `Missing admin CSRF token`，优先检查下面两类问题：

1. 前端是否在调用需要已有会话的写接口
	- 例如 `/api/admin/v1/users`、`/api/admin/v1/config/menu-items/publish` 这类接口，必须先有登录成功后的 `csrfToken`
2. 环境变量是否导致 cookie / CSRF 无法建立
	- `ADMIN_CSRF_SECRET`
	- `ADMIN_SESSION_COOKIE_NAME`
	- `ADMIN_SESSION_COOKIE_SECURE`
	- `ADMIN_SESSION_COOKIE_SAMESITE`
	- `ADMIN_SESSION_COOKIE_DOMAIN`
	- `ADMIN_GATEWAY_ALLOWED_ORIGINS`

当前首绑 MFA 的两个预登录接口：

- `POST /api/admin/v1/auth/mfa/enroll/begin`
- `POST /api/admin/v1/auth/mfa/enroll/verify`

不应该要求已有会话 CSRF。也就是说，如果登录页已经拿到 `MFA_ENROLLMENT_REQUIRED`，接下来进入首绑页时不应再因为“缺少 CSRF”而卡住。

### 2.3 初始化 bootstrap 管理员密码

`admin/gateway-admin/scripts/set_bootstrap_password.py` 的作用很直接：

- 读取 `gateway-admin` 库里的现有管理员账号
- 按邮箱定位目标 bootstrap 管理员
- 将你输入的明文密码转换成安全哈希
- 回写到 `admin_users.password_hash`

这个脚本不会创建管理员账号，也不会修改角色、MFA 状态或其他资料。它只负责一件事：给已经存在的 bootstrap 管理员写入初始密码。

适用场景：

- 本地第一次启用 `super@synapse.network`
- 测试环境需要激活某个 seed 管理员账号
- 旧库恢复后，发现 bootstrap 管理员仍然没有密码哈希

执行前确认：

- `gateway-admin` 的 Python 依赖已经安装完成
- `ADMIN_DATABASE_DSN` 指向正确的 `synapse_gateway_admin` 数据库
- 目标邮箱已经存在于 `admin_users` 表中

标准用法：

```bash
cd /Users/cliff/workspace/Synapse-Network/admin/gateway-admin
.venv/bin/python scripts/set_bootstrap_password.py \
	--dsn 'postgresql://synapse_admin_app:12345678@localhost:5432/synapse_gateway_admin' \
	--email 'super@synapse.network' \
	--password 'ReplaceWithStrongInitPassword'
```

参数说明：

- `--dsn`：`gateway-admin` 数据库连接串，脚本会直接用它读取和更新 `admin_users`
- `--email`：要初始化密码的 bootstrap 管理员邮箱
- `--password`：要写入的新明文密码，脚本内部会自动做 hash

成功时的输出示例：

```text
bootstrap password initialized for super@synapse.network (adm_super_admin)
```

常见用法示例：

初始化超级管理员：

```bash
cd /Users/cliff/workspace/Synapse-Network/admin/gateway-admin
.venv/bin/python scripts/set_bootstrap_password.py \
	--dsn 'postgresql://synapse_admin_app:12345678@localhost:5432/synapse_gateway_admin' \
	--email 'super@synapse.network' \
	--password 'SuperAdmin#2026!'
```

初始化运营管理员：

```bash
cd /Users/cliff/workspace/Synapse-Network/admin/gateway-admin
.venv/bin/python scripts/set_bootstrap_password.py \
	--dsn 'postgresql://synapse_admin_app:12345678@localhost:5432/synapse_gateway_admin' \
	--email 'ops@synapse.network' \
	--password 'OpsInit#2026!'
```

常见失败与处理：

- `admin user not found: <email>`
  - 说明目标邮箱在当前数据库里不存在，先检查你连的是不是正确库，再确认该 bootstrap 管理员是否已 seed
- 数据库连接失败
  - 优先检查 `--dsn` 是否指向 `synapse_gateway_admin`，以及本机 PostgreSQL、账号权限是否正常
- 初始化成功但仍然无法登录
  - 先确认密码输入无误
  - 再确认该管理员是否 `require_mfa=true`
  - 如果是 bootstrap 管理员，通常还需要提供已经 seed 的 TOTP 验证码，或者对“未绑定 MFA”的测试账号走首次绑定流程

推荐校验动作：执行成功后，立即用该账号走一次登录接口验证，而不是等到联调时再发现密码没初始化。

### 2.4 重置未绑定 MFA 的联调测试管理员

如果你要反复验证这条链路：

- 正确密码登录
- 返回 `428 MFA_ENROLLMENT_REQUIRED`
- 调 `/api/admin/v1/auth/mfa/enroll/begin`
- 调 `/api/admin/v1/auth/mfa/enroll/verify`
- 再进入 dashboard

推荐不要每次手工创建随机邮箱，而是直接用 `scripts/reset_mfa_enrollment_test_admin.py` 重置同一个测试管理员。

这个脚本会做两件事：

- 如果目标邮箱已经存在，先删除它的 session、enrollment challenge、MFA factor、role binding 和用户记录
- 再重新创建一个 `require_mfa=true`、但没有任何 active TOTP factor 的测试管理员

默认测试账号：

- 邮箱：`mfa-enroll-test@synapse.network`
- 密码：`EnrollUser#2026!`
- 角色：`platform_ops_admin`

标准用法：

```bash
cd /Users/cliff/workspace/Synapse-Network/admin/gateway-admin
.venv/bin/python scripts/reset_mfa_enrollment_test_admin.py \
	--dsn 'postgresql://synapse_admin_app:12345678@localhost:5432/synapse_gateway_admin'
```

执行成功后，你应该用下面这个账号直接验证登录首步：

```text

password: EnrollUser#2026!
expected result: 428 MFA_ENROLLMENT_REQUIRED
```

如果你想换成别的测试邮箱或密码：

```bash

.venv/bin/python scripts/reset_mfa_enrollment_test_admin.py \
	--dsn 'postgresql://synapse_admin_app:12345678@localhost:5432/synapse_gateway_admin' \
	--email 'qa-mfa-enroll@synapse.network' \
	--password 'QaEnroll#2026!' \
	--display-name 'QA MFA Enrollment Test' \
	--role-key 'platform_ops_admin' \
	--unsafe-allow-non-test-email
```

如果你只想删除这个联调测试管理员，不重新创建：

```bash

.venv/bin/python scripts/reset_mfa_enrollment_test_admin.py \
	--dsn 'postgresql://synapse_admin_app:12345678@localhost:5432/synapse_gateway_admin' \
	--cleanup-only
```

注意：

- 这个脚本只适合“专门用于 MFA enrollment 联调”的测试账号，不应用在正式管理员账号上
- 默认只允许操作 `mfa-enroll-test@synapse.network`；如果你传入别的邮箱，脚本会直接拒绝执行
- `super@synapse.network`、`ops@synapse.network` 这类 bootstrap 管理员绝对不要拿这个脚本去 reset，否则会把真实 seed 账号改造成测试账号

- 这个脚本不会写入 active TOTP，所以第一次密码登录时本来就应该收到 `MFA_ENROLLMENT_REQUIRED`

### 重新绑定MFA
```sql
DELETE FROM admin_sessions
WHERE admin_id = (
  SELECT admin_id FROM admin_users WHERE lower(email) = lower('super@synapse.network')
);

DELETE FROM admin_mfa_enrollment_challenges
WHERE admin_id = (
  SELECT admin_id FROM admin_users WHERE lower(email) = lower('super@synapse.network')
);

DELETE FROM admin_mfa_factors
WHERE admin_id = (
  SELECT admin_id FROM admin_users WHERE lower(email) = lower('super@synapse.network')
);
```

说明：

- 这组 SQL 只用于“让一个已经绑定过 MFA 的账号重新进入 enrollment 流程”
- 不需要删除 `admin_users` 和 `admin_user_role_bindings`
- 更推荐对专用联调测试账号执行，而不是对 `super@synapse.network` 这种 bootstrap 超管执行

## 6. 菜单配置中心发布说明

`/menu-config` 已切到真实 draft / publish 流程，运维上需要理解这两个阶段的职责：

- draft：后台配置人员正在编辑的草稿版本，允许频繁增删改，不对线上侧边栏直接生效
- published：当前所有后台管理员实际看到的全局菜单版本，只有在执行 publish 后才更新

对应的运行时行为：

- `GET /api/admin/v1/config/menu-items?stage=draft` 用于配置工作台读取草稿
- `GET /api/admin/v1/config/menu-items?stage=published` 用于后台壳子和普通管理员读取生效版本
- `POST/PATCH/DELETE /api/admin/v1/config/menu-items` 只修改 draft
- `POST /api/admin/v1/config/menu-items/publish` 才会把当前 draft 发布为新的 published

发布前准备：

- 确认数据库已经执行 `docker-compose/postgres/init/003_gateway_admin_projection_views.sql` 里的 admin config bootstrap 段
- 确认执行 publish 的账号具备 `super_admin` 角色
- 如果前端和后端分开部署，确认 `admin-front` 指向的新 `gateway-admin` 已完成发布

发布后的可见效果：

- 管理员刷新后台页面后，`AdminShell` 会重新拉取 published 菜单配置
- 普通管理员只能看到 published，因此不会读到未发布草稿
- 如果 `gateway-admin` 临时不可用，前端会退回静态菜单种子，避免控制面不可进入

## 7. 生产建议

- 如果是单机或开发机，优先使用 `start-local.sh`。
- 如果是正式生产，优先使用 `start-prod.sh + systemd`，不要长期手工 `nohup`。
- `EXECUTION_WORKER_ENABLED=true` 时，建议至少保持一个稳定实例常驻；多实例部署也没问题，execution job 抢占走数据库原子 claim，不靠 Redis 锁。
- `.env.local` 不要提交到仓库，敏感配置必须由部署机注入。
- 标准化生产示例见 `docs/systemd生产部署示例.md`。

## 8. 推荐操作流程

### 7.1 首次启动

```bash
cd /Users/cliff/workspace/Synapse-Network/admin/gateway-admin
cp .env.example .env.local
sh scripts/ops/start-local.sh
sh scripts/ops/status.sh
```

启动脚本现在只负责拉起 `uvicorn`，不再自动执行 admin bootstrap SQL。这样可以避免每次重启都隐式依赖一段 schema 修复逻辑，把“服务启动”和“数据库修复”拆成两个明确动作。

如果旧的 PostgreSQL volume 缺表，尤其是 `admin_execution_jobs`、`admin_execution_attempts` 这一类 execution worker 依赖表，请手动执行 `scripts/apply_migrations.py`。

如果 `ADMIN_DATABASE_DSN` 使用的是应用账号，而不是 schema owner，那么请额外配置 `ADMIN_DATABASE_MIGRATION_DSN`。原因很简单：应用账号通常只有读写现有表权限，没有 `CREATE TABLE` / `ALTER TABLE` 权限，手工补 migration 时会直接失败。

如果日志里已经出现过 `relation "admin_execution_jobs" does not exist`，可以先手动补跑：

```bash
cd /Users/cliff/workspace/Synapse-Network/admin/gateway-admin
ADMIN_DATABASE_MIGRATION_DSN='postgresql://<schema-owner>@<host>:5432/synapse_gateway_admin' \
./.venv/bin/python scripts/apply_migrations.py
sh scripts/ops/restart.sh local
```
