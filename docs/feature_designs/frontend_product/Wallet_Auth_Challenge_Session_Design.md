# Wallet Auth: Challenge vs Session Design

## 1. Purpose

This document defines the auth boundary and UX/security trade-offs for wallet sign-in in Synapse Network.

Goals:

1. Make auth behavior easy to understand for users and developers.
2. Keep replay resistance strong (challenge).
3. Keep product usability high (session).
4. Ensure docs, config, and runtime behavior stay aligned.

## 2. Core Concepts

### 2.1 Challenge (wallet-signing challenge)

Challenge is a short-lived, one-time message generated by backend and signed by wallet.

It is used to prove: "the current user controls this wallet now".

Characteristics:

1. One-time use.
2. Short TTL.
3. Bound to wallet address.
4. Invalid after consume or timeout.

It is not a long-running application session.

### 2.2 Session (platform auth session)

Session is a backend-issued bearer token (JWT) after signature verification.

It is used to authorize API calls to Synapse platform.

Characteristics:

1. Carries wallet identity (`sub`).
2. Has longer TTL than challenge.
3. Represents platform session state.
4. Can be invalidated by expiry or wallet mismatch.

It is not a wallet-level blockchain permission; it is platform-level API auth.

## 3. Challenge vs Session

| Item | Challenge | Session |
|---|---|---|
| Main role | Prove wallet control | Authorize platform API |
| Trigger | `/api/v1/auth/challenge` | `/api/v1/auth/verify` success |
| Lifetime | Short | Medium/long |
| Reuse | No (one-time) | Yes (until expiry) |
| Storage | Pending cache (server) | JWT + client storage |
| Security risk if long TTL | Replay window increases | Lower (token still signed/exp bounded) |

## 4. Should both be 24h?

Short answer: No.

1. Challenge should not be 24h. A long challenge TTL significantly increases replay exposure if signed payload leaks.
2. Session can be 24h (or longer with refresh-token design), because it is already an issued auth artifact with explicit expiry and server-side verification.

## 5. Recommended TTL Strategy

### 5.1 Recommended now (balanced)

1. `AUTH_CHALLENGE_TTL_SEC = 600` (10 min).
2. `AUTH_TOKEN_TTL_SEC = 86400` (24 h).

Why:

1. 10 min challenge reduces UX failures during wallet popup/network lag.
2. 24 h session avoids frequent re-sign in day-to-day dashboard use.
3. Security remains acceptable for current stage if JWT secret and HTTPS are enforced.

### 5.2 Higher-security mode

1. `AUTH_CHALLENGE_TTL_SEC = 300` (5 min).
2. `AUTH_TOKEN_TTL_SEC = 3600` (1 h).

### 5.3 Future production-hardening

1. Keep challenge short (5-10 min).
2. Use short access token (15-60 min) + refresh token (7-30 days).
3. Add revocation list and device/session management.

## 6. UX Design Rules

1. If challenge expired, show human-readable message and auto-request a new challenge.
2. Avoid clearing session on transient wallet reconnect (grace window).
3. Distinguish errors clearly:
   - challenge expired/signature invalid
   - session expired
   - wallet changed
4. Warn before destructive sign-out actions.
5. If wallet is connected (including reconnect) but session is missing, frontend should auto-attempt one authorization challenge once, then fall back to explicit manual retry.
6. Trigger challenge explicitly on sign-in/renew-session actions, and on fund-critical flows that require wallet signatures.

## 7. Current Runtime Mapping

Current runtime knobs (source of truth):

1. `AUTH_CHALLENGE_TTL_SEC`
2. `AUTH_TOKEN_TTL_SEC`

Current implementation behavior:

1. Challenge cache TTL follows `AUTH_CHALLENGE_TTL_SEC`.
2. JWT `exp` follows `AUTH_TOKEN_TTL_SEC`.
3. Verify response returns `expires_in` from backend config.
4. Frontend stores session expiry from backend `expires_in`.

## 8. Auth Flow (Current)

1. User connects wallet from RainbowKit connect flow.
2. Frontend automatically triggers one-time session authorization after successful user-initiated connect.
3. Frontend requests challenge.
4. Wallet signs challenge.
5. Frontend submits signature for verification.
6. Backend verifies signature + challenge validity.
7. Backend issues session token with `expires_in`.
8. Frontend stores token and calls protected APIs.

UX fallback:

1. If automatic authorization is cancelled or fails, top-right wallet badge exposes explicit `Authorize Login` action for manual retry.
2. Wallet remains connected while session stays unauthenticated until retry succeeds.
3. Session-expired reconnect reminder is deduplicated to a single toast prompt (no repeated stack spam during the same expiry burst).

## 8.1 Operation Decision Matrix (When challenge/session is required)

| Operation | Need challenge now? | Need session token? | Why |
|---|---|---|---|
| Initial wallet sign-in | Yes | Not yet | Challenge is the login proof step |
| Re-login after session expires | Yes | Not yet | Need fresh wallet proof |
| Register / update / delete provider service | No (if session valid) | Yes | Platform write operation, owner-isolated by session subject |
| Rotate service key / ping own service | No (if session valid) | Yes | Sensitive provider operation |
| Parse cURL and autofill service definition (provider workspace) | No (if session valid) | Yes | Workspace-scoped mutation helper |
| List own services | No (if session valid) | Yes | Tenant-isolated read |
| Public service discovery | No | No | Public marketplace capability |
| Read own audit logs | No (if session valid) | Yes | Sensitive tenant logs |
| On-chain withdraw/claim signature | Wallet signature needed on-chain | Session optional for off-chain helper endpoints | This is blockchain authorization, not only platform auth |

Rule of thumb:

1. Challenge is only for obtaining or renewing session.
2. Session is for most off-chain platform API operations.
3. On-chain value movement always requires wallet/typed-data signature regardless of session.

Connect + Login merged policy:

1. For wallet connect and reconnect events, connect and session login are treated as one continuous flow when session is missing.
2. System attempts authorization once automatically immediately after connect/reconnect.
3. Manual `Authorize Login` remains available as deterministic recovery path.
4. Auth signing only supports single-account wallet selection at connect time. If multiple accounts are selected, frontend prompts user to keep one account and reconnect.

Wallet modal UX baseline:

1. Use compact RainbowKit modal (`modalSize=compact`) as default web login surface to avoid heavy full-screen feeling.
2. If a wallet app itself enters full-screen account selection, treat it as wallet-native behavior; frontend should still keep pre/post prompts concise and deterministic.

## 8.2 Page Auth Matrix (Frontend)

### Session-required pages (page-level)

1. `/provider/services/deploy` (canonical provider publish workflow)
2. `/provider/secrets` (canonical access key management)
3. `/dashboard/credentials` (credential issuance/revoke/audit)
4. `/dashboard/console` for authenticated data actions

Compatibility note:

1. Some `/dashboard/**` routes still exist as legacy aliases or implementation hosts.
2. Product and new docs should prefer `/provider/**` for Provider workspace links.

### Public-readable pages (no session required)

1. `/` (product intro)
2. `/blog`, `/about`
3. `/dashboard/services` public marketplace section (discover list)
4. `/dashboard/billing` with guest empty/zero state
5. `/provider/sell` and summary cards with guest-safe zeros

Behavior requirement:

1. Guest users can see what Synapse does and what public APIs/services exist.
2. Private wallet data (balances, usage, credentials, private services) must stay session-protected.
3. When session is missing, show empty/zero placeholders instead of crashing.

## 9. API/Doc Contract Requirements

1. `GET /api/v1/auth/challenge` must document challenge TTL and one-time semantics.
2. `POST /api/v1/auth/verify` must document `expires_in` as config-driven value.
3. Error responses should indicate challenge expiry vs session expiry.

## 10. Decision for Current Stage

Adopt this baseline:

1. Challenge: 10 minutes.
2. Session: 24 hours.
3. Keep one-time challenge semantics.
4. Keep wallet-switch hard reset.
5. Add refresh-token architecture in next iteration if cross-day persistence is needed.

## 11. Doc/Code Consistency Notes

1. Service-management routes (`/api/v1/services` create/list/update/delete, rotate-key, ping, parse-curl) are session-protected and owner-scoped.
2. Billing/refund/usage routes (`/api/v1/balance*`, `/api/v1/refund`, `/api/v1/refunds`, `/api/v1/usage/logs`) are session-protected and owner-scoped.
3. Discovery route (`/api/v1/services/discover`) and indexer health (`/api/v1/indexer/status`) remain public.
4. If docs claim service management or private billing routes are open/public, that is outdated and must be corrected.

Provider workspace naming note:

1. UI copy may use `API Service` and `Service Definition`.
2. Protocol/storage canonical terms still retain `Service Manifest` where required by backend schema and runtime contract docs.
