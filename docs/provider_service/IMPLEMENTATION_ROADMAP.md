# Provider Service 冷启动实施路线图（7 天 / 14 天 / 30 天）

7 天可执行任务清单见：[Provider Service 7 天任务清单（Backend / Provider Console / Marketplace / SDK）](./DAY7_TASKBOARD.md)

## 1. 目标

这份路线图不讨论“应该做什么服务”，而是回答另一个更残酷的问题：

**怎么在 30 天内，把冷启动从 PPT 变成一个真能跑、真有货、真能被 Agent 调用的市场。**

核心目标只有三个：

1. 让 Synapse Marketplace 不再是空货架
2. 让 Agent 能完成第一次真实的服务发现、报价、调用、返回
3. 让 Platform 用最少的人力先跑出第一批供给侧样板

## 2. 总体策略

冷启动不能一口气铺 20 个服务。

正确节奏是：

1. **7 天先做出 3 到 5 个真能调用的样板货**
2. **14 天补齐 Marketplace 的“看起来像市场”的供给密度**
3. **30 天开始做平台化复制能力，而不是继续手工堆服务**

一句话：

**前 7 天做样板，前 14 天做货架，前 30 天做复制系统。**

## 3. 7 天计划：先把第一批样板货挂上去

### 3.1 阶段目标

在 7 天内完成以下结果：

1. Platform 官方 Provider 账号可用
2. 至少 3 个冷启动服务已注册到 Synapse
3. 每个服务都能完成一次真实 invoke
4. SDK / demo 可直接展示调用结果
5. Marketplace 首页不再是空状态

### 3.2 必做服务

这 7 天不要贪多，只做下面 5 个中的至少 3 个，理想状态做满 5 个：

1. Web3 实时情绪指数
2. 智能合约漏洞深度审计模型
3. 链上巨鲸资金异动监控
4. 协议基本面情报包
5. GitHub 仓库与依赖安全体检

### 3.3 核心交付物

#### 交付物 A：Platform 官方 Provider 身份

必须完成：

1. 官方 Provider profile
2. payout account 绑定
3. service manifest 模板统一
4. `Platform Verified` 标签规则

#### 交付物 B：3 到 5 个服务的最小可调用版本

每个服务最小形态必须具备：

1. 清晰 `service_name`
2. 简洁 `description_for_model`
3. 最小 `input_schema`
4. 结构化 `output_schema`
5. 可用上游和缓存策略
6. 真实返回样例

#### 交付物 C：Demo 调用链路

必须至少打通一条完整链路：

1. discover 到服务
2. quote 返回定价
3. invoke 返回真实结果
4. 控制台或 SDK 能展示 response

### 3.4 7 天排期建议

#### Day 1

1. 定官方 Provider 身份和命名规范
2. 统一 5 个服务的 manifest 模板
3. 确认每个服务的免费上游、缓存 TTL、超时阈值

#### Day 2

1. 接入 Web3 实时情绪指数
2. 接入 协议基本面情报包
3. 输出结构化 schema 和 mock result

#### Day 3

1. 接入 链上巨鲸资金异动监控
2. 完成事件聚合、标签和解释字段
3. 确认 invoke 路径下性能可接受

#### Day 4

1. 接入 GitHub 仓库与依赖安全体检
2. 统一 OSV/GitHub/PyPI/npm 的结果层
3. 补最小错误码和降级返回

#### Day 5

1. 接入 智能合约漏洞深度审计模型
2. 跑通 `source -> scanner -> structured report`
3. 明确重型任务的同步 / 异步策略

#### Day 6

1. 完成 3 到 5 个服务注册
2. 完成 SDK 示例或控制台演示
3. 调整 Marketplace 展示顺序和官方标签

#### Day 7

1. 统一 smoke test
2. 输出公开 demo 文档
3. 复盘哪些服务值得进入 14 天扩展阶段

### 3.5 7 天验收标准

满足以下条件才算完成：

1. 至少 3 个服务可被 discover 到
2. 至少 3 个服务可被真实 invoke
3. 每个服务都有结构化 response 样例
4. 至少 1 条 Agent SDK 示例能串起来
5. 首屏 Marketplace 看起来像“有货可买”

## 4. 14 天计划：把样板货扩成像样的货架

### 4.1 阶段目标

14 天阶段的重点，不是继续手工做几个孤立服务，而是让 Marketplace 看起来已经有了品类密度和选择空间。

目标：

1. 上线 8 到 10 个官方冷启动服务
2. 形成 3 个以上明确品类
3. 每个品类至少有 2 个服务
4. 首页、搜索、标签、详情页开始具备“市场感”

### 4.2 建议新增服务

在第一波基础上补齐：

1. Gas 费用与执行窗口建议
2. 稳定币脱锚与储备监控
3. 合约源码/ABI 检索与函数解释
4. 交易解码与意图解释
5. 论文检索与三段式摘要

如果人力允许，再追加：

1. 地址画像与风险标签摘要
2. 开源依赖漏洞扫描
3. 代币流动性与交易深度快照

### 4.3 14 天核心交付物

#### 交付物 A：品类化货架

至少形成这 3 个类目：

1. Web3 Intelligence
2. Security & Audit
3. Research & Open Source

每个类目都要能支持：

1. 列表展示
2. 标签过滤
3. 官方服务优先露出

#### 交付物 B：基础运营能力

必须补齐：

1. 服务卡片标准文案
2. 调用示例
3. 错误码与降级说明
4. SLA / freshness 字段
5. 缓存策略说明

#### 交付物 C：基础监控能力

必须知道每个服务：

1. discover 曝光量
2. quote 次数
3. invoke 次数
4. invoke 成功率
5. P95 latency

### 4.4 14 天验收标准

1. 8 到 10 个服务可见
2. 其中至少 5 个可稳定 invoke
3. 已形成可筛选的 3 个品类
4. Demo 用户首次进入 Marketplace 不会觉得空
5. 已能从数据上看出哪些服务最值得继续投入

## 5. 30 天计划：从“Platform 自营样板”升级到“可复制的供给引擎”

### 5.1 阶段目标

30 天阶段的本质，不再是新增几个服务，而是把“Platform 自己做服务”沉淀成一套可复制的 Provider 工厂。

目标：

1. Marketplace 稳定保持 12 到 20 个服务供给
2. 官方服务形成标准接入模板
3. 第三方 Provider 开始能按模板接入
4. 平台开始知道哪些服务免费，哪些可以升级付费

### 5.2 30 天核心交付物

#### 交付物 A：Provider Service 模板化能力

至少要有：

1. 通用 manifest 模板
2. 通用上游适配器模板
3. 通用缓存 / 超时 / fallback 模板
4. 通用服务 smoke test 模板

#### 交付物 B：服务分层策略

每个成熟服务开始进入分层：

1. `free`：低频演示型
2. `pro`：更实时、更完整字段
3. `enterprise`：专属上游、专属配额、专属 callback

#### 交付物 C：第三方供给接入准备

要开始支持：

1. Provider onboarding 指南
2. Manifest 校验模板
3. 类目和标签规范
4. 官方推荐上游清单
5. 服务质量评分方法

#### 交付物 D：增长验证指标

30 天后必须能回答：

1. 哪个服务 discover 量最高
2. 哪个服务 quote 到 invoke 转化最好
3. 哪个服务最值得继续做付费升级
4. 哪个类目最能带动 Agent 首次付费调用

### 5.3 30 天验收标准

1. 12 到 20 个服务已上架
2. 至少 8 个服务可稳定 invoke
3. 至少 3 个服务具备升级为付费版的价值
4. 官方 Provider 模板化能力形成文档和代码骨架
5. 已具备吸引第三方 Provider 入场的最小示范效应

## 6. 按角色拆分执行责任

### 6.1 Product / Founder

负责：

1. 决定首批 5 个服务优先级
2. 定义服务卡片文案和市场定位
3. 决定哪些服务先免费、哪些保留低价

### 6.2 Backend / Gateway

负责：

1. 上游适配
2. schema 归一
3. timeout / cache / fallback
4. discover / quote / invoke 稳定性

### 6.3 Provider Console / Marketplace

负责：

1. 服务展示
2. 官方标签
3. 类目和筛选
4. demo request / response 展示

### 6.4 Ops / Analytics

负责：

1. 服务监控
2. 上游配额监控
3. 调用成功率和耗时监控
4. 冷启动阶段效果复盘

## 7. 风险与防呆

### 7.1 最容易犯的错

1. 一开始就做 20 个服务，结果每个都半死不活
2. 原样透传第三方 API，没有自己的结果层
3. 上游免费配额没控好，被打爆
4. 服务能 discover 但不能稳定 invoke
5. 首页摆了一堆名字，但没有一个真正可演示

### 7.2 风险控制建议

1. 所有服务先走缓存和超时兜底
2. 所有服务先给固定 demo input/output
3. 重型任务优先异步化或做简版模式
4. 首页只展示已经真实可调用的服务
5. 每周只追一个核心指标：`首次 discover -> invoke 转化`

## 8. 最小里程碑定义

### M1: 7 天

`Marketplace 从空货架变成有 3 到 5 个可调用样板服务`

### M2: 14 天

`Marketplace 从样板展示变成像样的品类货架`

### M3: 30 天

`Marketplace 从官方自营样板，升级成可复制的供给引擎`

## 9. 推荐执行顺序

如果只能按一条最短路径推进，建议严格照下面顺序：

1. 先把官方 Provider 账号和标签体系定下来
2. 先做 3 个最能打的服务，不要同时铺 20 个
3. 先打通 discover / quote / invoke，再优化 UI
4. 先把调用监控做出来，再讨论精细化增长
5. 先把自营服务跑通，再让第三方 Provider 入场

一句话结论：

**7 天要的是“有真货”，14 天要的是“像市场”，30 天要的是“能复制”。**

只要这套节奏走对，Synapse 的冷启动就不是靠讲故事，而是靠真实供给把市场点燃。
