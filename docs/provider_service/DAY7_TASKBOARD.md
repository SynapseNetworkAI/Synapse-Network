# Provider Service 7 天任务清单（Backend / Provider Console / Marketplace / SDK）

## 1. 目标

这份任务清单只服务一件事：

**把 7 天计划拆成可以直接分工、直接开干、直接验收的执行板。**

拆分原则：

1. 不写抽象口号，只写可交付任务
2. 按四条线拆：`Backend / Provider Console / Marketplace / SDK`
3. 每个任务都尽量具备：产出物、依赖、完成标准

## 2. 7 天总验收口径

7 天结束时，必须满足：

1. 官方 Provider 身份可用
2. 至少 3 个服务完成注册并能被 discover
3. 至少 3 个服务能真实 invoke
4. SDK 有至少 1 条端到端示例
5. Marketplace 首屏可展示首批官方服务

## 3. 四条线的边界

### 3.1 Backend

负责：

1. 上游适配
2. 服务结果归一
3. discover / quote / invoke 可用性
4. 缓存、超时、fallback、错误码

### 3.2 Provider Console

负责：

1. 官方 Provider 资料与服务录入
2. Manifest 表单与字段校验
3. 服务发布、修改、状态确认

### 3.3 Marketplace

负责：

1. 服务列表露出
2. 官方标签与类目展示
3. 服务详情和调用样例展示

### 3.4 SDK

负责：

1. 示例调用脚本
2. discover -> quote -> invoke 串联
3. demo 输出和错误示例

## 4. 优先服务范围

7 天内只围绕这 5 个服务推进，不额外开新坑：

1. `web3_sentiment_index`
2. `smart_contract_audit`
3. `whale_flow_monitor`
4. `protocol_fundamental_brief`
5. `oss_security_healthcheck`

## 5. Day 1 任务清单

### 5.1 Backend

- 任务：确定 5 个服务的统一响应骨架
  产出物：统一 response schema 草案
  完成标准：5 个服务至少共享 `service`, `sources`, `freshness`, `result`, `errors` 字段约定
- 任务：确定上游接入策略
  产出物：每个服务的上游、缓存 TTL、timeout、fallback 表
  完成标准：5 个服务都明确主源、备源、降级返回
- 任务：确定 invoke 执行模式
  产出物：同步 / 异步判定表
  完成标准：明确 `smart_contract_audit` 是否先做简版同步调用

### 5.2 Provider Console

- 任务：定义官方 Provider 身份
  产出物：Provider name、slug、logo、bio、tag 方案
  完成标准：形成唯一官方 Provider 命名，不和未来第三方混淆
- 任务：整理 manifest 必填字段
  产出物：首批 5 个服务 manifest 模板
  完成标准：每个服务都有 `service_name`、`description_for_model`、pricing、input/output schema 初稿

### 5.3 Marketplace

- 任务：定义首批官方服务的展示规则
  产出物：`Platform Verified` 标签和默认排序策略
  完成标准：明确首屏优先露出官方服务
- 任务：定义类目映射
  产出物：5 个服务到类目的映射表
  完成标准：至少分成 `Web3 Intelligence`、`Security & Audit`、`Research & Open Source`

### 5.4 SDK

- 任务：定义 demo 路径
  产出物：首批演示脚本清单
  完成标准：至少确定 1 条完整示例使用哪个服务、输入什么、输出什么
- 任务：统一调用示例格式
  产出物：request/response 示例模板
  完成标准：统一 Python SDK 示例输出格式

## 12. 跨线依赖表

### 12.1 Backend 先于其他线的依赖

1. 没有统一 schema，Provider Console 无法稳定录入
2. 没有可用 invoke，SDK 和 Marketplace 都只能摆样子

### 12.2 Provider Console 对 Marketplace 的依赖

1. 没有规范化 manifest，Marketplace 文案和字段会乱
2. 没有官方标签规则，用户看不出哪些是平台样板货

### 12.3 SDK 对 Backend 的依赖

1. 只要 response schema 不稳，SDK 示例就会反复返工
2. 只要错误码不稳，demo 就不可靠

## 13. 每日站会建议问题

每天站会只问这 5 个问题：

1. 今天新增了几个“真实可调用”的服务，而不是新增了几个文档项？
2. 哪个服务现在能 discover，但还不能 invoke？
3. 哪个服务 invoke 成功，但结果还不够像产品？
4. 哪条线今天阻塞了其他三条线？
5. 如果今晚要演示，哪 3 个服务最稳？

## 14. 最小执行原则

7 天内，所有任务都服从这 4 条：

1. 先打通真实链路，再追求完美抽象
2. 先做 3 到 5 个能打的样板货，不做 20 个半成品
3. 先让 Agent 能消费结构化结果，不做原始上游透传
4. 先让 Marketplace 看起来有货，再去卷运营细节

一句话收口：

**这 7 天的任务清单，不是为了“写完计划”，而是为了让 Synapse 在一周内从空市场变成有真货、有调用、有演示的赛博超市。**
