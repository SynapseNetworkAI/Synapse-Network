# 充值 / 退款审批流程

本文档描述 Synapse 当前代码实现下，买家充值、平台账本同步、失败补偿，以及退款 / 提现审批的完整流程边界。目标不是画 PPT，而是把“谁在自动推进、谁需要人工审批、谁负责补偿”说清楚。

## 1. 总体原则

- 链上合约负责收钱与最终资产托管，不负责高频业务编排。
- gateway 负责登记充值意图、推进链下账本、做幂等、防重放、审计与补偿。
- admin/gateway-admin 只负责人工审批和受控内部执行，不直接改 gateway 真相账本。
- 自动任务优先处理可程序化确认的路径；只有进入异常区时才升级到人工审批。

## 2. 买家充值完整流程

### 2.1 正常路径

1. 买家先登录 gateway，会话里的 owner 由服务端 token 绑定，不信任前端裸传地址。
2. 前端或 SDK 调用 `POST /api/v1/balance/deposit/intent`，提交 `txHash`、`amountUsdc` 和 `X-Idempotency-Key`。
3. gateway 落一条 deposit intent，状态初始为 `PENDING_CONFIRMATION` 或 `PENDING`，此时链下账本还没有加钱。
4. 用户把 USDC 真正打进合约后，gateway 有两条确认路径：
   - 主动确认：调用 `POST /api/v1/balance/deposit/intents/{deposit_intent_id}/confirm`，提交 `eventKey` 和确认数。
   - 被动确认：后台 indexer 轮询链上收据和 backfill，自动扫描待确认 intent。
5. 当 gateway 在链上 receipt 中匹配到合法 deposit event 后，会调用原子确认逻辑，把 intent 标记为 `CONFIRMED`，同时把金额记入买家账本余额，并写入审计流水。
6. 到这一步，钱已经从合约侧成功进入平台可用账本，可以参与后续扣费与清算。

### 2.2 钱如何从合约同步到平台

同步动作不是靠前端回调拍脑袋，而是靠 gateway 的 deposit indexer 和原子确认仓储完成。

- gateway 周期执行 `process_pending_deposit_intents_once(storage)`。
- 它会读取所有 `PENDING_CONFIRMATION` / `PENDING` intent。
- 对每条 intent：
  - 校验 `txHash`、`ownerAddress`、`amountUsdc` 是否有效。
  - 从链上拿 receipt，并匹配 vault deposit event。
  - 用 `eventKey` 做防重放，避免同一笔链上事件二次入账。
  - 通过原子确认逻辑一次性完成：intent 状态推进、余额入账、processed event 记录、审计写入。

换句话说，链上成功只是第一阶段；只有 gateway 原子确认成功，平台账本才真正认为“这笔钱可用”。

## 3. 如果同步到平台失败，会不会自动补偿

会，而且是两层补偿，不是只靠人肉点按钮。

### 3.1 自动补偿层

gateway 的 `run_v2_deposit_indexer(...)` 常驻循环会持续做三件事：

1. backfill 扫描历史区块，防止事件漏监听。
2. `process_pending_deposit_intents_once(...)` 推进所有待确认 intent。
3. 周期性 reconciliation，对比链上 vault 余额和链下账本义务。

这意味着：

- 如果链上交易已成功，但某次同步因为网络抖动、节点超时、进程重启中断，待确认 intent 会在后续轮次继续被捞起。
- 如果监听漏掉事件，backfill 会重新扫块并把漏事件补回。
- 如果账本和链上出现差额，reconciliation 会把差额、告警状态和最后错误码持久化到 runtime state，并反映到后台运维读模型。

### 3.2 人工补偿层

不是所有失败都该无限自动重试。进入以下情况时，需要升级人工审批：

- deposit intent 长时间未被自动确认，且已有明确链上成功证据。
- reconciliation 出现差额告警，需要受控修复。
- 某笔历史脏数据需要显式 replay，不能让后台任务盲目重放。

这时管理员会在 `gateway-admin` 提交 `deposit_repair` 审批单。审批通过后，会生成 execution job，worker 自动调用 gateway 内部命令 `POST /api/v1/admin/deposits/replay` 做受控补偿执行。

## 4. 什么时候需要审核

### 4.1 充值

正常充值不需要人工审核。

充值只有在“自动确认 / 自动补偿无法安全闭环”时，才进入后台审批，典型就是 `deposit_repair`：

- 链上已成功，但账本没入账。
- backfill / pending processor 多轮后仍未恢复。
- reconciliation 出现差额，需要人工确认后做定向 replay。

### 4.2 退款

退款在 gateway 里会先做风控分类，不是所有退款都自动通过。

当前代码里的人工审核条件包括：

- 退款金额大于等于 `500 USDC`。
- 退款类型属于人工申诉类退款。
- 24 小时内检测到异常拆单退款模式。

命中后，refund intent 会进入 `PENDING_MANUAL_REVIEW`。这类退款不能直接完成，必须由 reviewer 提供审核决策后，才能调用完成接口。

在 admin 控制面里，这对应 `refund_approve` 审批单。审批通过后，execution job 会自动调用 `POST /api/v1/admin/refunds/{refund_id}/complete`，把 reviewer 信息和 review decision 一起传给 gateway。

### 4.3 提现

卖家提现也不是全自动。

当前代码中，当提现金额大于等于 `100 USDC` 时，会进入 `PENDING_MANUAL_REVIEW`；否则可以自动批准生成签名 ticket 或进入自动可完成状态。

人工审核提现在 admin 控制面里对应 `withdrawal_approve` 审批单。审批通过后，execution job 会自动调用 `POST /api/v1/admin/providers/withdrawals/{withdrawal_id}/complete`，由 gateway 完成最终链下状态推进。

## 5. 后台审批与自动执行是怎么串起来的

### 5.1 审批生成执行任务

1. 管理员提交审批单，状态为 `SUBMITTED`。
2. reviewer 审核通过后，审批状态变为 `APPROVED_PENDING_EXECUTION`。
3. approval service 同时生成一条 execution job，状态为 `PENDING`。

### 5.2 worker 自动消费

`gateway-admin` 启动后会拉起 execution worker：

- 周期扫描 `PENDING` execution jobs。
- 先在存储层做原子 `claim`，把 job 从 `PENDING` 抢占成 `RUNNING`。
- 抢占成功的实例才允许往下执行 gateway 内部命令。
- 执行完成后把 job、attempt、approval、audit 一次性更新为 `SUCCEEDED` / `FAILED` 对应状态。

这个原子 claim 是生产多实例安全的关键点。不开这个保险杠，多个 Pod 同时扫队列就可能重复执行同一条内部命令。

## 6. 生产开启 worker 会不会有并发问题

会有并发场景，但现在不是裸奔。

### 6.1 会存在的并发场景

- 多个 `gateway-admin` 副本同时启动 worker。
- 同一时刻有人手动 retry 某个 job，同时 worker 也扫到了它。
- 一个 job 被列表查询看到时还是 `PENDING`，下一毫秒已经被别的实例抢走。

### 6.2 当前的安全策略

为了解决这个问题，execution job 现在不是“先查出来再假设自己能执行”，而是：

1. 先读到候选 job。
2. 真正执行前，在存储层做原子 `claim_execution_job(...)`。
3. 只有状态仍然匹配 `PENDING` 或 `FAILED/CANCELLED` 的那一个执行者，才能把 job 改成 `RUNNING`。
4. claim 失败的实例直接跳过，不会继续调用 gateway 内部命令。

因此，生产开启 worker 后仍然有并发访问，但不会把同一条 job 当成“谁都能执行”的共享玩具。

## 7. 自动补偿与人工审批的边界

该自动的自动，该审批的审批，边界如下：

- 自动处理：链上确认、补扫历史事件、推进普通 pending deposit intent、周期性 reconciliation。
- 人工审批：deposit repair、需要 reviewer 决策的 refund、需要 reviewer 决策的 withdrawal。
- 自动执行审批结果：审批通过后由 worker 自动消费 execution job，不再要求管理员手动点 retry。

这条边界非常重要。自动系统负责最终一致性，人类只负责异常裁决，不直接去篡改账本真相。

## 8. 关键接口与后台任务清单

### 8.1 gateway 用户侧接口

- `POST /api/v1/balance/deposit/intent`
- `POST /api/v1/balance/deposit/intents/{deposit_intent_id}/confirm`
- `POST /api/v1/refund`
- `POST /api/v1/refunds/{refund_id}/complete`
- `POST /api/v1/providers/withdrawals`
- `POST /api/v1/providers/withdrawals/{withdrawal_id}/complete`

### 8.2 gateway 管理侧内部接口

- `POST /api/v1/admin/deposits/replay`
- `POST /api/v1/admin/refunds/{refund_id}/complete`
- `POST /api/v1/admin/providers/withdrawals/{withdrawal_id}/complete`

### 8.3 后台任务

- `run_v2_deposit_indexer(...)`
- `process_pending_deposit_intents_once(...)`
- backfill 扫描
- reconciliation 检查
- `gateway-admin` execution worker

## 9. 落地结论

- 充值不是“上链成功就算平台到账”，而是“链上成功 + gateway 原子确认入账”才算到账。
- 同步失败有自动补偿，不是只能靠人。
- 自动补偿兜不住时，才走 `deposit_repair` 审批。
- 退款和提现只有命中风控条件才需要人工审核。
- 审批通过后的执行已经自动化，但前提是 worker 在生产打开并配置好内部 gateway 调用凭据。

这套设计的核心不是多写了几个状态，而是把自动一致性、人工裁决、受控执行三层边界彻底拆开。这样系统才像清算基础设施，而不是后台运营同学手点按钮的脚本集合。
