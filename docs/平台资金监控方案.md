# 平台资金监控方案

## 1. 目标

本文档定义 Synapse 平台资金监控的统一口径，目标不是只看单个余额，而是建立一套覆盖以下全链路的数据漏斗和监控面板：

1. 充值链路
2. Agent 调用与计费链路
3. 平台收入沉淀
4. 合约 / Vault 总金额
5. Provider 收益累积
6. 用户可退款资金
7. Provider 可提现资金
8. 对账差额与异常处置

这份文档同时回答三个问题：

1. `Absolute delta` 是什么
2. `Signed difference` 是什么
3. `Ledger obligation` 是什么，是否等于用户可退款总额

## 2. 三个核心指标是什么意思

### 2.1 Ledger obligation

当前代码口径里，`Ledger obligation` 是 **平台对 Owner 消费资金桶的账本义务总额**。

它来自 Gateway reconciliation 任务中的这条逻辑：

1. 读取 ledger
2. 汇总 `total_consumer_obligation()`
3. 与链上 `chain vault` 余额做比较

也就是说，当前实现里它更接近：

$$
Ledger\ obligation = Owner\ liability
$$

而不是：

$$
Ledger\ obligation = Owner\ liability + Provider\ payable + Platform\ income
$$

所以，答案很明确：

`Ledger obligation` **不是** “用户 consumer 可以提现的总金额”。

更准确地说：

1. 它表示平台账本对买家侧消费资金桶的当前义务
2. 它是 vault 理论上至少应该覆盖的买家侧负债面
3. 它不等于用户当前立刻可退款金额
4. 它也不包含 Provider 收益应付和平台收入池

为什么它不等于“用户可退款总金额”：

1. 用户退款走的是 `consumer_refund` 独立流程
2. refund 还要经过风控、状态机和冻结 / 审核逻辑
3. `Ledger obligation` 是账本负债口径，不是前台可操作余额口径

因此，业务理解上应该拆成两层：

1. `Ledger obligation`：账本对 Owner 的义务
2. `Refundable consumer balance`：在风控与状态机约束下，用户实际可发起退款的金额

### 2.2 Signed difference

`Signed difference` 是带方向的差额，当前后端口径是：

$$
Signed\ difference = Chain\ vault - Ledger\ obligation
$$

解释：

1. 大于 `0`：链上 Vault 余额高于买家侧账本义务，属于 `vault surplus`
2. 小于 `0`：链上 Vault 余额低于买家侧账本义务，属于 `vault deficit`
3. 等于 `0`：当前这条 reconciliation 口径下完全平衡

它的价值不是看“差了多少”，而是看“差额方向”。

### 2.3 Absolute delta

`Absolute delta` 是绝对差额，不带方向，回答的问题只有一个：

$$
Absolute\ delta = |Chain\ vault - Ledger\ obligation|
$$

解释：

1. 它不关心 surplus 还是 deficit
2. 它只告诉 operator 当前偏差量级有多大
3. 更适合做告警阈值和首页哨兵指标

## 3. 当前指标口径的限制

当前 admin reconciliation 面板里的 `Ledger obligation` 是为 **充值对账** 服务的，不是为“全平台资金监控总账”服务的。

所以它有两个天然限制：

1. 它只看买家侧消费义务
2. 它没有把 Provider 应付和平台收入一起纳入全局资金视图

这意味着当前指标适合回答：

1. 充值入金有没有进账
2. 买家侧资金是否被 Vault 覆盖

但它不够回答：

1. 平台总资产与总负债是否完整对齐
2. Provider 收益是否被足额覆盖
3. 平台收入是否真实沉淀
4. 整个平台 Treasury 是否健康

所以，后续监控必须区分两种视角：

1. `Deposit reconciliation view`
2. `Treasury full-chain monitoring view`

## 4. 目标监控模型

平台资金监控建议拆成五层：

1. 入金漏斗
2. 收费漏斗
3. 收入沉淀漏斗
4. 出金漏斗
5. Treasury / Vault 总账视图

### 4.1 Layer A: 入金漏斗

关注问题：钱有没有真的从链上进入平台可用消费余额。

关键阶段：

1. `deposit_intent_created`
2. `tx_broadcasted`
3. `chain_receipt_confirmed`
4. `indexer_event_matched`
5. `ledger_confirmed`
6. `consumer_available_released`

推荐核心指标：

1. intent 数量
2. 链上成功数量
3. indexer 匹配成功数量
4. 最终 confirmed 数量
5. `pending deposit count`
6. `failed deposit count`
7. deposit 从广播到入账的 P50 / P95 延迟

推荐漏斗公式：

$$
Deposit\ completion\ rate = \frac{ledger\ confirmed}{deposit\ intent\ created}
$$

$$
Deposit\ sync\ lag = chain\ confirmed - ledger\ confirmed
$$

数据源：

1. `synapse_vault_deposits`
2. `synapse_processed_deposit_events`
3. `synapse_deposit_attempts`
4. `synapse_runtime_state.deposit_reconciliation_state`
5. `synapse_audit_events`

### 4.2 Layer B: 调用计费漏斗

关注问题：一次成功调用有没有正确完成 reserve、capture、收入分配与审计闭环。

关键阶段：

1. `quote_reserved`
2. `invocation_started`
3. `invocation_succeeded`
4. `budget_captured`
5. `consumer_charged`
6. `provider_payable_accrued`
7. `platform_income_accrued`

推荐核心指标：

1. quote 数量
2. invoke 成功数量
3. capture 数量
4. 今日扣费总额 `today charge`
5. Provider 收益新增额
6. 平台收入新增额
7. `capture / success` 差值
8. 失败 release 数量

关键不变量：

设本次调用价格为 `P`，平台费为 `F`，Provider 净收入为 `N`，则必须满足：

$$
P = F + N
$$

并且：

$$
consumer\ decrease = provider\ payable\ increase + platform\ income\ increase
$$

数据源：

1. `synapse_service_quotes`
2. `synapse_invocations`
3. `synapse_budget_events`
4. `synapse_ledger_entries`
5. `synapse_audit_events`

### 4.3 Layer C: 平台收入沉淀漏斗

关注问题：平台抽成有没有从“应该赚到”变成“已经沉淀在平台账本里”。

关键阶段：

1. `charge recognized`
2. `platform fee split calculated`
3. `platform_revenue ledger written`
4. `platform income balance updated`

推荐核心指标：

1. `platform income`
2. 今日新增平台收入
3. 平台收入累计值
4. 按 service / provider / owner 分组的平台收入贡献

建议监控公式：

$$
Platform\ income\ balance = current\ platform\_revenue\ bucket\ balance
$$

数据源：

1. `synapse_account_balances` 中 `platform_revenue`
2. `synapse_ledger_entries`
3. `synapse_invocations`

### 4.4 Layer D: 出金漏斗

关注问题：资金流出有没有被正确分类到 `consumer_refund` 和 `provider_withdrawal`，并受控推进。

这里必须明确拆开两条链：

1. 用户退款链
2. Provider 提现链

#### 4.4.1 用户退款链

关键阶段：

1. `refund_intent_created`
2. `risk_checked`
3. `approved_auto_or_manual`
4. `consumer_balance_frozen`
5. `ticket_signed`
6. `refund_completed`

核心指标：

1. 今日退款金额 `today refund`
2. pending manual review 数量
3. refund completed 数量
4. refund reject 数量
5. refundable consumer balance

#### 4.4.2 Provider 提现链

关键阶段：

1. `withdrawal_intent_created`
2. `risk_checked`
3. `provider_balance_locked`
4. `approved_auto_or_manual`
5. `ticket_signed`
6. `withdrawal_completed`

核心指标：

1. 今日提现金额 `today withdrawal`
2. `pending withdrawals`
3. Provider 可提现余额
4. Provider 锁仓余额
5. Provider completed withdrawal 数量

数据源：

1. `synapse_vault_withdrawals`
2. `synapse_account_balances`
3. `synapse_ledger_entries`
4. `synapse_audit_events`

## 5. Treasury 全局监控口径

这是本文最关键的部分。

如果平台要监控“整个链路”，不能只看 `Ledger obligation`，必须再加三条口径：

1. `Owner liability`
2. `Provider payable`
3. `Platform income`

### 5.1 三个桶的业务含义

1. `Owner liability`
   平台对买家消费资金池的当前义务。
2. `Provider payable`
   平台已确认、但尚未最终链上结转给 Provider 的收益义务。
3. `Platform income`
   已经沉淀在平台账本内、归平台所有的收入池。

### 5.2 目标总账公式

建议新增一个 Treasury 总账监控视角：

$$
Treasury\ expected\ gross = Owner\ liability + Provider\ payable + Platform\ income
$$

然后把它与链上金库余额比较：

$$
Treasury\ signed\ difference = Chain\ vault - Treasury\ expected\ gross
$$

$$
Treasury\ absolute\ delta = |Chain\ vault - Treasury\ expected\ gross|
$$

这组指标比当前 `Deposit reconciliation` 更完整，因为它覆盖：

1. 充值沉淀的买家资产
2. 调用结算形成的 Provider 应付
3. 平台已经赚到的收入

### 5.3 为什么要保留两套 delta

建议同时保留两套：

1. `Deposit delta`
   $$
   |Chain\ vault - Ledger\ obligation|
   $$
   用于监控买家入金与消费侧对账。
2. `Treasury delta`
   $$
   |Chain\ vault - (Owner\ liability + Provider\ payable + Platform\ income)|
   $$
   用于监控整个平台资金总账是否闭环。

这样 operator 就不会再混淆“充值对账视图”和“平台 Treasury 总账视图”。

## 6. 建议的监控面板

建议 `Finance / Reconciliation / Treasury` 分成四个面板，而不是把所有数字挤在一个卡片区。

### 6.1 Panel A: Deposit Funnel

展示：

1. deposit intents
2. chain confirmed
3. ledger confirmed
4. pending deposits
5. deposit sync lag
6. deposit P95 delay

### 6.2 Panel B: Billing Funnel

展示：

1. quote reserve
2. invocation success
3. budget capture
4. today charge
5. provider payable increment
6. platform income increment

### 6.3 Panel C: Outflow Funnel

展示：

1. refund intents
2. refund pending review
3. refund completed
4. withdrawal intents
5. pending withdrawals
6. withdrawal completed

### 6.4 Panel D: Treasury Sentinel

展示：

1. chain vault
2. owner liability
3. provider payable
4. platform income

6. treasury signed difference
7. absolute delta
8. reconciliation alert

## 7. 关键告警规则

### 7.1 入金告警

1. `pending deposits` 连续增长
2. `chain confirmed - ledger confirmed` 超阈值
3. deposit P95 延迟超 SLA

### 7.2 计费告警

1. invocation success 明显高于 capture 数
2. capture 金额与 ledger entries 金额不守恒
3. platform income 连续为 0 但 charge 持续增长

### 7.3 Treasury 告警

1. `deposit absolute delta` 超阈值
2. `treasury absolute delta` 超阈值
3. `treasury signed difference < 0` 持续多个窗口
4. chain vault 下降但 provider / refund 完成量没有同步增长

### 7.4 出金告警

1. pending withdrawals 激增
2. refund manual review 激增
3. ticket signed 后长时间未 completed

## 9. 落地建议

### 9.1 先做

1. 保留当前 `Ledger obligation / Signed difference / Absolute delta` 作为充值对账视图
2. 在 Finance / Treasury 里新增：
   - `Owner liability`
   - `Provider payable`
   - `Platform income`
   - `Treasury signed difference`
   - `Treasury absolute delta`
3. 单独建设三条漏斗：
   - deposit funnel
   - billing funnel
   - outflow funnel

### 9.2 再做

1. 给每个漏斗补 P50 / P95 时延
2. 给每个漏斗补异常积压数
3. 让 admin 支持按 owner / provider / service drill-down

## 10. Admin 控制台信息架构落地

上面的指标定义如果不落到页面层，最终还是会退化成“知道概念，但值班时找不到入口”。

所以 admin 控制台建议固定成三层页面分工：

1. `/dashboard` 只看全局健康和漏斗摘要
2. `/finance` 只看资金总账、趋势和出入金压力
3. `/finance/reconciliation` 只看差额、证据、队列和修复动作

核心原则：

1. 首页不做深度调查，只做值班哨兵
2. Finance 不做 deposit repair 细节，只做资金面判断
3. Reconciliation 不承担全局经营总览，只聚焦差额和补偿闭环

### 10.1 `/dashboard` 首页卡片

首页的职责只有两个：

1. 让值班管理员 10 秒内知道系统是否处于资金风险态
2. 明确下一步该进入 Finance、Reconciliation、Approvals 还是 System

首页建议放 4 组卡片。

#### Group A: Global Sentinels

卡片：

1. `Control plane status`
   展示 `overallStatus`、诊断摘要、当前建议动作。
2. `Deposit absolute delta`
   展示当前充值对账绝对偏差。
3. `Treasury absolute delta`
   展示 Treasury 总账绝对偏差。
4. `Pending approvals`
   展示待审核总量。

设计要求：

1. 只放最高优先级数字
2. 所有卡片必须可跳转
3. 红色只用于真正要人工介入的异常

#### Group B: Flow Snapshot

卡片：

1. `Today deposit`
2. `Today charge`
3. `Today refund`
4. `Today withdrawal`

这一组回答的是“今天钱怎么流”。

#### Group C: Queue Pressure

卡片：

1. `Pending deposits`
2. `Pending withdrawals`
3. `Deposit exceptions`
4. `Audit alerts`

这一组回答的是“今天哪里堵了”。

#### Group D: Funnel Mini Panels

首页只放缩略版漏斗，不放全量图表：

1. `Deposit funnel summary`
   展示 `intent -> chain confirmed -> ledger confirmed`
2. `Billing funnel summary`
   展示 `quote reserve -> invocation success -> budget capture`
3. `Outflow funnel summary`
   展示 `refund pending -> refund completed` 与 `withdrawal pending -> withdrawal completed`

首页这里必须是摘要，不做 drill-down 表格。

### 10.2 `/finance` 页面卡片

`/finance` 的职责是回答：平台总账现在健康吗，钱沉淀在哪些桶里，今天资金进出压力怎样。

它不应该承担逐笔证据调查。

`/finance` 建议固定成 5 组卡片。

#### Group A: Treasury Core

卡片：

1. `Chain vault`
2. `Owner liability`
3. `Provider payable`
4. `Platform income`

这是 Finance 页的第一屏，属于全局总账视图。

#### Group B: Treasury Delta

卡片：

1. `Treasury signed difference`
2. `Treasury absolute delta`
3. `Deposit signed difference`
4. `Deposit absolute delta`

解释：

1. Treasury delta 看全局总账
2. Deposit delta 看买家入金对账
3. 两套都保留，避免误判

#### Group C: Flow Volume

卡片：

1. `Today deposit`
2. `Today charge`
3. `Today refund`
4. `Today withdrawal`

#### Group D: Flow Trend

图表：

1. `Deposit vs charge trend`
2. `Refund vs withdrawal trend`
3. `Platform income accumulation trend`

#### Group E: Liability and Outflow Pressure

卡片：

1. `Refundable consumer balance`
2. `Provider available to withdraw`
3. `Provider locked balance`
4. `Pending withdrawals`
5. `Pending deposits`

这一组把“能退多少钱、能提多少钱、堵了多少单”放在同一个视图里。

当前 `gateway-admin` 的 backend contract 建议固定为：

1. `refundableConsumerBalanceUsdc`：先使用 `consumer_wallet.available_balance` 聚合值作为 operator proxy。
2. 这个字段当前不是逐 origin 退款上限的严格数学定义，因为 SQL 投影层还没有把 invocation refund origin 归因和账本余额完全拼起来。
3. `providerAvailableToWithdrawUsdc`：使用 `provider_wallet.available_balance` 聚合值。
4. `providerLockedBalanceUsdc`：使用 `provider_wallet.pending_balance + frozen_balance` 聚合值。
5. `pendingWithdrawalCount`：统计所有尚未完成的 provider withdrawal 队列状态，包含 `REQUESTED`、`SIGNED`、`APPROVED_AUTO`、`PENDING_MANUAL_REVIEW`，并兼容历史遗留状态。

### 10.3 `/finance/reconciliation` 页面卡片

`/finance/reconciliation` 的职责不是做经营总览，而是做金融事故前线调查。

它必须聚焦四件事：

1. 差额有多大
2. 差额方向是什么
3. 问题更像入金漏记、出金积压还是账本漂移
4. 现在能用什么证据和动作修复

建议固定成 6 组卡片。

#### Group A: Reconciliation Hero

卡片：

1. `Chain vault`
2. `Ledger obligation`
3. `Signed difference`
4. `Absolute delta`

这是当前充值对账视图的核心，不要混入 Treasury 总账口径。

#### Group B: Supporting Buckets

卡片：

1. `Owner liability`
2. `Provider payable`
3. `Platform income`

这一组不是 hero 指标，而是帮助 operator 判断差额来源。

#### Group C: Deposit Evidence

卡片：

1. `Pending deposits`
2. `Deposit exceptions`
3. `Chain confirmed but not ledger confirmed`
4. `Deposit P95 sync delay`

#### Group D: Outflow Evidence

卡片：

1. `Today refund`
2. `Today withdrawal`
3. `Pending withdrawals`
4. `Recently completed outflows`

当前 `gateway-admin` 的 reconciliation evidence contract 建议固定为：

1. `chainConfirmedNotLedgerConfirmedCount`：`synapse_deposit_attempts.stage = RECEIPT_CONFIRMED`，但 `synapse_vault_deposits.status != CONFIRMED` 的 tx hash 数量。
2. `depositP95SyncDelaySeconds`：从 `RECEIPT_CONFIRMED` 到账本 `CONFIRMED` 的同步时延 P95，单位秒。
3. `todayRefundUsdc` 与 `todayWithdrawalUsdc`：以 `COMPLETED` 作为 canonical finished status，同时兼容历史 `CONFIRMED`。
4. `recentlyCompletedOutflowsUsdc`：最近 6 小时内已经完成的 `consumer_refund + provider_withdrawal` 金额，用来辅助解释链上余额的短时下降。

#### Group E: Action Queues

卡片 / 列表：

1. `Priority approvals`
2. `Deposit repair approvals`
3. `Pending withdrawal reviews`
4. `Audit alerts`

#### Group F: Recommended Actions

只给 operator 当前该做什么，不给泛泛建议。

动作卡：

1. `Open deposit repair queue`
2. `Open pending withdrawals`
3. `Open audit trail`
4. `Run diagnostics`

### 10.4 三页之间的跳转关系

必须固定以下跳转，不允许每个页面自己发明链接。

1. `/dashboard` 的 `Deposit absolute delta` 跳到 `/finance/reconciliation`
2. `/dashboard` 的 `Pending approvals` 跳到 `/approvals`
3. `/finance` 的 `Treasury absolute delta` 跳到 `/finance/reconciliation`
4. `/finance` 的 `Pending withdrawals` 跳到 `/approvals` 或 `/withdrawal-reviews`
5. `/finance/reconciliation` 的 action cards 跳到具体工作队列

### 10.5 不该放在这些页面的内容

为了避免 IA 再次失焦，下面这些内容不要塞错页面：

1. `/dashboard` 不放逐笔充值表和逐笔 audit 明细
2. `/finance` 不放 deposit replay 操作按钮
3. `/finance/reconciliation` 不放大段经营趋势图和非对账经营 KPI
4. 退款审核、提现审核、repair 执行都应该跳到对应 queue 或 detail 页面，而不是在总览页直接做高危动作

## 11. 结论

一句话总结：

1. `Ledger obligation` 目前是 **买家侧账本义务**，不是“用户可提现总额”
2. `Signed difference` 是带方向差额
3. `Absolute delta` 是绝对差额
4. 如果你要监控整个平台资金真相，必须从“充值对账”升级到“Treasury 总账 + 漏斗监控”

最小可用监控闭环应该是：

**Deposit Funnel -> Billing Funnel -> Platform Income -> Refund / Withdrawal Funnel -> Treasury Sentinel**

只有这样，平台才能真正看清：

1. 钱有没有进来
2. 钱有没有被正确扣费
3. 平台有没有赚到钱
4. Provider 有没有形成应收
5. 用户能不能退款
6. Provider 能不能提现
7. 合约金库能不能覆盖整个平台的真实账本义务
