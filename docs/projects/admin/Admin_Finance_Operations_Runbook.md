# 管理后台财务操作手册

本文是平台管理后台的财务操作 Runbook，面向：

- `finance_admin`
- `finance_reviewer`
- `risk_admin`
- `risk_reviewer`
- `compliance_auditor`
- `platform_ops_admin`

用于指导下面这些高频或高风险操作：

- 充值异常排查
- 补账申请与补账执行
- 冻结 / 解冻账户
- 提现审核
- 退款审核
- 风险升级与应急处置

目标是把“后台怎么做”从口头经验变成标准 SOP。

## 1. 使用范围与基本原则

### 1.1 本手册适用范围

本手册只适用于平台后台控制面，不适用于：

- 普通用户前台
- 开发调试脚本直接操作数据库
- 未经审批的临时生产修复

### 1.2 核心原则

所有财务操作都遵循以下原则：

1. 先查询，后判断，再申请，最后执行
2. 审批系统批准的是“允许执行”，不是“直接改账本”
3. 资金主真相仍由 `gateway` 受控逻辑维护
4. 所有高危动作必须有审批单与审计链
5. 任何应急操作都必须可复盘

## 2. 后台财务操作分级

建议把后台财务操作按风险拆成四级。

### 2.1 `O1` 低风险只读操作

例如：

- 查充值状态
- 查 intent 状态
- 查看用户余额
- 查看提现状态
- 查看退款状态

要求：

- 只读权限
- 自动审计访问行为

### 2.2 `O2` 中风险申请操作

例如：

- 发起补账申请
- 发起冻结申请
- 发起解冻申请
- 发起退款审批单

要求：

- 有业务理由
- 有关联对象
- 自动生成审批单

### 2.3 `O3` 高风险审批操作

例如：

- 审批提现
- 审批补账
- 审批余额修复
- 审批高风险白名单放行

要求：

- 发起人与审批人分离
- 风险信息齐全
- 审批理由必填

### 2.4 `O4` 极高风险执行或应急操作

例如：

- 大额手工补账执行
- 手工余额调整
- 大规模冻结
- 紧急暂停某类资金流

要求：

- 双审批或超管复核
- 强审计
- 事后复盘

## 3. 财务后台日常操作总流程

所有财务后台动作都建议走统一框架：

1. 接收工单或系统告警
2. 查询相关交易、余额、intent、审计、风险信息
3. 判断问题属于哪一类
4. 根据本手册选择对应 SOP
5. 若涉及写操作，必须创建审批单
6. 审批通过后执行
7. 核对执行结果
8. 留存审计与处理结论

## 4. 充值异常排查 SOP

### 4.1 适用场景

用户反馈：

- 链上充值成功，但平台余额未增加
- 页面长时间显示充值处理中
- 同一笔充值被重复或异常标记

### 4.2 排查输入信息

优先收集：

- 用户钱包地址 `owner_address`
- 充值交易哈希 `txHash`
- 充值时间区间
- 充值金额
- 相关工单号

### 4.3 必查数据

后台应至少查看：

1. 链上交易是否成功
2. receipt 中是否存在可识别的 deposit event
3. `synapse_deposit_intents` 中是否有对应记录
4. `processed_deposit_event_keys` 是否已有该 `eventKey`
5. 用户当前 `available_balance / pending_balance / frozen_balance`
6. 是否存在相关审计和审批历史

### 4.4 问题分类

常见分类如下：

#### A 类：链上失败

特征：

- `receipt.status != 1`

处理：

- 不补账
- 回复用户链上交易失败
- 记录工单结论

#### B 类：链上成功，但平台没有 intent

特征：

- 链上有事件
- 平台无对应 intent

补充说明：

- 前端开发者控制台现在会在发起充值交易后立即把 `txHash + amountUsdc` 持久化到本地待恢复队列。
- 如果页面刷新、钱包弹窗关闭较慢，或 receipt 确认晚于当前页面生命周期，用户重新回到控制台并完成 session 鉴权后，前端会自动检查 receipt 并重提 `deposit intent`。
- 因此排查前先确认用户是否已经重新进入控制台并恢复会话，避免把“可自动恢复中的前端状态”误判成真实资金未到账。

处理：

- 进入补账申请 SOP

#### C 类：intent 存在，但一直停留在 `PENDING_CONFIRMATION`

特征：

- 链上成功
- intent 存在
- 未进入 confirmed

处理：

- 优先走 replay / repair 申请

#### D 类：intent 已 `CONFIRMED`，但余额仍不对

特征：

- intent 状态已确认
- 余额未体现或 pending 未释放

处理：

- 进入 repair 申请
- 检查是否属于系统自动 repair 可修场景

#### E 类：事件已被去重跳过

特征：

- `processed_deposit_event_keys` 已存在该 `eventKey`

处理：

- 不允许直接重复入账
- 需要升级为人工复核，确认是否是历史错误去重或重复充值

## 5. 补账申请与执行 SOP

### 5.1 什么时候允许发起补账

满足以下条件时才允许发起：

1. 链上交易成功
2. 金额与用户申诉一致或可解释
3. 当前账本没有正确反映该笔资金
4. 已完成前置排查

### 5.2 不允许直接补账的情况

以下情况不允许直接进入补账：

1. receipt 无法确认
2. 交易失败
3. 事件已明显重复，且没有异常证据
4. 余额差异原因尚未查清

### 5.3 补账申请单必填字段

- 工单号
- 用户钱包地址
- `txHash`
- `eventKey`（若已知）
- 链上金额
- 当前平台账本状态
- 补账原因
- 风险等级
- 建议动作：`replay` / `repair` / `manual_adjust_request`

### 5.4 补账执行优先级

建议按以下优先级处理：

1. 优先 `replay_deposit_tx`
2. 其次 `repair confirmed intent`
3. 再其次小范围 backfill
4. 最后才考虑极高风险的人工余额调整申请

### 5.5 补账执行 SOP

1. 财务管理员发起补账申请
2. 审批人核对链上证据与账本状态
3. 审批通过后执行器执行 replay / repair
4. 再次检查：
   - intent 状态
   - `processed_event_keys`
   - `available_balance`
5. 写入执行结果和处理结论

### 5.6 补账后验收项

必须确认：

1. 用户余额与链上事实一致
2. 没有重复入账
3. 审计日志完整
4. 审批链完整

## 6. 账户冻结 / 解冻 SOP

### 6.1 适用场景

- 可疑充值行为
- 高风险退款套利
- 可疑提现
- 安全事件调查

### 6.2 冻结前检查

必须查看：

- 账户当前余额构成
- 是否有待处理提现
- 是否有高风险标签
- 是否已有未完成审批单

### 6.3 冻结申请 SOP

1. 风控或财务发起冻结申请
2. 填写冻结原因和冻结范围
3. 指定是否影响：
   - 充值入账
   - 提现
   - 退款
   - 服务调用
4. 审批通过后执行冻结
5. 通知相关观察面板或工单系统

### 6.4 解冻 SOP

1. 必须有解冻依据
2. 必须检查风险是否已解除
3. 必须确认没有遗漏异常资金动作
4. 审批通过后执行解冻

### 6.5 冻结类审计重点

必须记录：

- 谁发起
- 谁审批
- 冻结范围
- 受影响账户
- 解冻条件

## 7. 提现审核 SOP

### 7.1 审核前检查

提现审核前必须查看：

1. 用户可用余额是否充足
2. 是否存在冻结余额
3. 是否命中风控标签
4. 是否超出自动审核阈值
5. 是否存在同类提现历史异常

### 7.2 可直接拒绝的情况

- 余额不足
- 风控明确红灯
- 账户被冻结
- 提现资料异常

### 7.3 需要升级审批的情况

- 大额提现
- 新注册账户高额提现
- 风险评分偏高
- 同一地址短时间多次提现

### 7.4 提现审批 SOP

1. 财务查看提现单详情
2. 查看风控结论与历史行为
3. 做出：`approve / reject / escalate`
4. 审批通过后执行放行
5. 回填链上 txHash 或内部完成状态

### 7.5 提现后核查

必须确认：

- 状态迁移正确
- 资金未重复扣减
- 审批审计齐全

## 8. 退款审核 SOP

### 8.1 审核前检查

必须查看：

1. 原始交易或原始 usage 是否存在
2. 已退款金额与可退款额度
3. 是否存在异常拆单
4. 当前账户风险状态

### 8.2 退款审核结论

- `approve`
- `reject`
- `manual_review`
- `escalate`

### 8.3 退款审批 SOP

1. 核验原单真实性
2. 核验退款额度剩余额度
3. 查看风险规则命中情况
4. 审批通过后执行退款完成逻辑
5. 校验余额与审计结果

## 9. 配置相关财务操作 SOP

### 9.1 平台费率调整

步骤：

1. 发起费率变更申请
2. 明确 before / after
3. 说明业务原因和影响范围
4. 审批通过后执行配置更新
5. 确认是否需要公告或延迟生效

### 9.2 风控阈值调整

步骤：

1. 明确阈值修改原因
2. 说明预计影响范围
3. 在生产环境必须走审批
4. 生效后观察告警和误杀率

## 10. 应急处置 SOP

### 10.1 适用场景

- 大规模充值漏账
- 大规模异常提现
- 资金账本与链上余额差异扩大
- 风控策略配置失误

### 10.2 应急动作原则

1. 先止血，再修复
2. 优先冻结高风险路径
3. 禁止未经记录的直接数据库修改
4. 所有 emergency 操作必须有理由和复盘

### 10.3 典型应急流程

1. 接到告警
2. 快速确认影响范围
3. 触发应急审批或紧急权限流程
4. 执行限流 / 冻结 / 暂停某类动作
5. 启动专项排查
6. 形成补救计划
7. 复盘并沉淀结论

## 11. 禁止事项

后台财务操作中，明确禁止：

1. 未审批直接改余额主表
2. 前端页面直接连主库做修复
3. 发起人审批自己的补账单
4. 无工单、无理由执行手工修复
5. 只改 UI 状态，不改真实业务状态
6. 先删审计再补账

## 12. 后台财务操作最小页面建议

如果后续做 `admin-front`，建议第一期至少提供这些页面：

1. 充值异常排查页
2. 补账申请页
3. 提现审核页
4. 退款审核页
5. 账户冻结/解冻页
6. 审批任务中心
7. 审计查询页
8. 应急操作记录页

## 13. 第一阶段最小落地建议

建议第一期先让后台支持这几个闭环：

1. 查询充值异常
2. 提交补账申请
3. 审批补账申请
4. 执行 replay / repair
5. 查询提现并完成审批
6. 查询退款并完成审批

不要第一期就开放“手工直接改余额”。

## 14. 最终建议

1. 后台财务操作必须围绕“查询 -> 审批 -> 执行 -> 验收 -> 审计”五步走。
2. 补账优先使用 replay / repair / backfill 等受控逻辑，不要一上来就人工改余额。
3. 冻结、提现、退款、补账都必须归入审批体系和审计体系。
4. 应急场景允许快速处置，但不允许绕过记录。
5. 第一阶段后台能力重点应放在异常排查与受控修复，而不是开放万能修改按钮。
