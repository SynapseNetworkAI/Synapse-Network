# Synapse 文档迁移与治理方案

## 1. 背景判断

当前 `docs/` 的主要问题，不是完全没有结构，而是已经存在一套结构后，又持续叠加了：

1. root `docs/` 下的单文件真理源
2. 六个官方模块
3. `agent/` 运行时 canonical 设计层（当前过渡层）
4. `03_Projects/` 项目集中维护层
5. `admin/`、`provider_service/` 等专题层
6. `feature_designs/` 孵化设计层
7. 中文补充文档
8. `plan/` 与 `exec-plans/` 历史与执行计划层

问题因此演变为四类：

1. 同一主题在多个层级重复出现，但抽象层次没有被持续维护。
2. 有些文档已经被显式标记为非 canonical 或旧设计，但仍然容易被误读为当前真相。
3. 代码、数据库、接口、运维命令的真实来源分散在 Markdown、SQL、migration、项目 README 和局部规则中，缺少统一约束。
4. 新功能增加时，团队容易先加新文档，再补索引和边界，导致目录继续变厚、真理源继续分叉。

因此，这次不建议再做一次“大搬家式重构”。

更合理的路线是：

1. 先把现有文档全部纳入统一治理视图
2. 明确每类文档的职责和生命周期
3. 再分批收敛散落内容到稳定目录
4. 用规则和流程阻止后续再次漂移

## 2. 目标

本方案要达成五个结果：

1. 任何主题都只有一个明确的 canonical 文档入口。
2. 代码、数据库、API、运维说明的真理源层级固定，不再靠经验判断。
3. 新文档只能进入明确目录，不再向 root `docs/` 和专题层散落。
4. 历史设计、孵化设计、补充说明与当前真理源彻底分层。
5. 后续新增功能时，文档更新能跟代码、测试、数据库变更一起完成，而不是事后补票。

## 3. 总体原则

### 3.1 一主题一真理源

每个主题必须只有一个 canonical 入口，例如：

1. 运行时身份、discover / quote / invoke、budget 模型，短期以 `docs/agent/` 为准；长期应并入 `00-06` 对应模块。
2. 主业务流程，以 `docs/03_Core_Workflows/` 为准。
3. 数据库结构与资金模型，以 `docs/04_Database_Design/` 和对应 SQL / migration 为准。
4. 项目职责、目录入口、本地开发和运维说明，以 `docs/03_Projects/` 为准。
5. 管理后台的系统级控制面设计，以 `docs/admin/` 为准。
6. 快速查阅型内容，以 `docs/06_Reference/` 为准。

其他文档只能：

1. 解释
2. 补充
3. 指向
4. 归档

不能并列重定义。

### 3.2 代码和数据库优先于解释性文档

当说明与实现不一致时，真理源顺序固定为：

1. 数据库结构：SQL bootstrap / migration > 数据库设计说明 > quick reference
2. API 契约：代码中的 schema / router / tests > 参考索引 > 高层说明
3. 运维命令：脚本 / package.json / 项目 AGENTS > 运维文档说明
4. 管理后台投影：view SQL / migration > admin API contract > 页面说明

也就是说，Markdown 不是唯一真相，而是“面向人类的稳定解释层”。

### 3.3 结构稳定优先于重新命名

当前六模块 + `agent/` + `03_Projects/` 的大框架已经可用。

因此不建议再次大规模改目录名。

建议采用“保留主结构，治理散点，并逐步消化 `agent/` 过渡层”的演进方案。

### 3.4 先聚合治理视图，再物理迁移

“先聚合”不是把所有文件立刻搬到一个临时目录，而是先完成：

1. 全量分类
2. 责任归属
3. canonical 认定
4. 被替代关系
5. 迁移批次

只有分类清楚后，才做物理移动、合并、归档或 banner 标记。

## 4. 推荐的可持续目录结构

建议保留当前主骨架，并补齐治理层与归档层职责：

```text
docs/
├── AGENTS.md
├── ARCHITECTURE.md
├── README.md
├── 文档迁移.md
├── 00_Governance/
│   ├── README.md
│   ├── Documentation_Lifecycle.md
│   ├── Documentation_Standards.md
│   ├── Ownership_And_Review_Matrix.md
│   └── Drift_Checklist.md
├── 01_Product_Frontend/
├── 01_Product_Vision/
├── 02_System_Architecture/
├── 03_Core_Workflows/
├── 03_Projects/
├── 04_Database_Design/
├── 05_DevOps_Deployment/
├── 06_Reference/
├── admin/
├── feature_designs/
├── exec-plans/
└── archive/
```

说明：

1. `00_Governance/` 是新增治理层，用来放文档生命周期、命名规则、owner 规则、漂移检查清单。
2. 现有六模块继续保留，不做大规模重命名。
3. `agent/` 不建议作为长期独立层保留；它更适合在迁移完成后按主题并入 `02_System_Architecture/`、`03_Core_Workflows/`、`04_Database_Design/`、`06_Reference/`，必要时少量入口回到 root 全局文件。
4. `03_Projects/` 继续作为项目集中维护层。
5. `feature_designs/` 明确只做孵化设计，不再承载长期真理源。
6. 新增 `archive/` 作为未来退役设计和历史专题的统一归档区；长期建议把 `plan/` 的纯历史材料也逐步并入这里。

## 5. 各层职责定义

### 5.1 根级全局入口

保留这些 root 文件作为顶层入口：

1. `AGENTS.md`
2. `ARCHITECTURE.md`
3. `README.md`
4. `文档迁移.md`

root 不应继续新增大量业务单文件。

下面这些 root 单文件，后续应逐步回收入模块：

1. `api.md`
2. `Gateway_Error_Codes.md`
3. `Gateway_Database_Design.md`
4. `测试文档.md`
5. `平台资金监控方案.md`
6. `充值退款审批流程.md`

它们不是都要立刻删除，而是应逐步变成：

1. 模块内正式文档
2. 或模块 quick reference
3. 或带 banner 的补充文档

### 5.2 `agent/`（过渡层，不建议长期保留）

职责：

1. Agent runtime 协议
2. 身份与预算模型
3. Service manifest 模型
4. SDK 集成主协议

不应承载：

1. 项目本地启动命令
2. 页面 IA 细节
3. admin 控制面局部流程

更关键的是：

1. `agent/` 虽然大量描述的是 gateway runtime 设计，但它不是 `gateway/` 项目私有文档。
2. 这些内容同时约束 `gateway`、`frontend`、`sdk/python`、`provider_service` 的交互边界。
3. 所以它不应该并入 `docs/03_Projects/gateway/`，而应按主题被拆回官方模块。

建议的最终归宿：

1. 身份、角色、控制面与执行面边界：并入 `02_System_Architecture/`
2. discover / quote / invoke、provider 注册、提现与审计链路：并入 `03_Core_Workflows/`
3. 数据模型重建、Agent-first schema、账本对象：并入 `04_Database_Design/`
4. Agent-facing contract、manifest 字段、SDK 对接约束：并入 `06_Reference/`
5. 只有顶层跨模块的总述，才保留在 root `ARCHITECTURE.md` 或 root 全局入口中

结论：

1. `agent/` 可以并入 `00-06`。
2. 但不建议一次性整体平移；应按主题拆分迁移。
3. 在迁移完成前，`agent/` 作为过渡层继续存在，避免当前 canonical 链接突然断裂。

### 5.3 六个官方模块

职责如下：

1. `01_Product_Frontend/`: 产品前台、信息架构、设计系统、前端体验原则
2. `02_System_Architecture/`: 拓扑、bounded context、依赖边界、系统职责
3. `03_Core_Workflows/`: 入金、调用、结算、Provider 注册、提现等主流程，也承接原 `agent/` 中的 runtime 主链路协议说明
4. `04_Database_Design/`: 结构、关系、账本、幂等、一致性，也承接原 `agent/` 中的数据模型重建与对象分层说明
5. `05_DevOps_Deployment/`: 本地环境、CI/CD、观测、故障响应、运行手册
6. `06_Reference/`: API 索引、错误码、对象参考、开发/测试/验证入口，也承接原 `agent/` 中稳定的 agent-facing contract / manifest / SDK 参考

补充：

1. `01_Product_Frontend/` 不吸收 `agent/` 的协议定义。
2. `02_System_Architecture/` 吸收 `agent/` 的系统边界、控制链路与执行链路、角色模型。
3. `03_Core_Workflows/` 吸收调用生命周期和运行时流程。
4. `04_Database_Design/` 吸收 Agent-first 数据模型。
5. `06_Reference/` 吸收稳定字段、对象与 SDK / API quick reference。

### 5.4 `03_Projects/`

职责：

1. 项目边界
2. 代码位置
3. 本地开发入口
4. 项目级运维说明
5. 项目级 canonical 工程规则

不应再承载：

1. 平台级协议定义
2. 跨项目数据库模型
3. 全局资金规则

### 5.5 `admin/`

职责：

1. Admin control plane 设计
2. RBAC
3. Approval / review 语义
4. 管理后台投影和控制边界

与 `docs/03_Projects/gateway-admin/` 的分界：

1. `docs/admin/` 写系统设计和控制面语义
2. `docs/03_Projects/gateway-admin/` 写本地开发、运行、环境变量、ops

### 5.6 `feature_designs/`

职责：

1. 未上升为 canonical 的专题设计
2. 正在试验的交互、信息架构、专题方案

必须增加明确规则：

1. 一旦实现稳定并成为当前事实，canonical 内容必须回写官方模块。
2. 原文件保留为补充或迁入归档，不继续承担当前真理源职责。

### 5.7 `archive/`

职责：

1. 历史计划
2. 已退役设计
3. 被替代但仍有审计价值的方案

任何 archive 文档必须有三项元信息：

1. 被什么替代
2. 何时退役
3. 为什么保留

## 6. 先聚合，再拆分的迁移方法

### Phase 0: 建立全量文档台账

先不要搬文件，先做一份台账，至少记录每份文档的：

1. 路径
2. 主题
3. 当前状态：canonical / supplementary / incubation / legacy / archive
4. owner
5. 对应代码目录
6. 对应数据库真理源
7. 是否与其他文档重复
8. 建议动作：保留 / 合并 / 拆分 / 归档 / 加 banner

建议由 `docs/00_Governance/Ownership_And_Review_Matrix.md` 和文档台账一起承载。

### Phase 1: 先收口 root 散点文档

第一批优先处理 root `docs/` 的散点单文件，因为这些文件最容易造成“看起来像真理源，但位置不稳定”。

建议动作：

1. `api.md` 迁入或镜像到 `06_Reference/`
2. `Gateway_Error_Codes.md` 归入 `06_Reference/`
3. `Gateway_Database_Design.md` 归入 `04_Database_Design/` 作为 quick reference
4. `测试文档.md` 并入 `06_Reference/04_Development_Testing_and_Integration_Reference.md` 或 `05_DevOps_Deployment/`
5. `平台资金监控方案.md` 并入 `05_DevOps_Deployment/` 与 `docs/admin/` 的 observability / projection 设计
6. `充值退款审批流程.md` 并入 `03_Core_Workflows/` 或 `docs/admin/`，取决于最终判定它更偏主流程还是审批控制面

这一步做完后，root `docs/` 只保留真正的入口和治理文件。

### Phase 2: 再处理专题层重复

重点检查：

1. `docs/admin/` 与 `docs/03_Projects/gateway-admin/`
2. `docs/agent/` 与 `02_System_Architecture/`、`03_Core_Workflows/`、`04_Database_Design/`、`06_Reference/`
3. `docs/feature_designs/` 与 `01_Product_Frontend/`
4. 中文补充文档与英文 canonical 模块

处理原则：

1. 系统设计保留在专题层
2. 本地运行说明保留在项目层
3. 旧设计保留但加 banner
4. 已被替代的 IA 和旧命名，不再出现在主阅读路径

### Phase 2.5: 拆分 `agent/` 进入 `00-06`

这一步建议单独执行，不和其他主题混批：

1. 先为每篇 `agent/*.md` 指定目标模块。
2. 先迁移正文，再在原文件顶部加“已迁移到哪里”的过渡说明。
3. 保留 1-2 个版本周期的 redirect 窗口。
4. 最后再删除 `agent/` 目录或只保留一个 README 级跳转壳。

建议映射：

1. `00_Platform_Role_Identity_Model.md` -> `02_System_Architecture/`
2. `01_Agent_Runtime_Product_Architecture.md` -> `02_System_Architecture/` + root `ARCHITECTURE.md`
3. `02_Discovery_Quote_Invoke_API_Design.md` -> `03_Core_Workflows/` + `06_Reference/`
4. `03_Service_Manifest_Field_Standard.md` -> `06_Reference/`
5. `04_Credential_Budget_Risk_Model.md` -> `02_System_Architecture/` + `04_Database_Design/`
6. `05_Dashboard_IA_and_Onboarding.md` -> `01_Product_Frontend/` 或归档
7. `06_Build_For_Agent_Database_Rebuild.md` -> `04_Database_Design/`
8. `07_Agent_SDK_Integration_Guide.md` -> `06_Reference/`
9. `agent_design.md` -> 视内容判断并入 `02_System_Architecture/` 或归档

### Phase 3: 最后统一 archive

完成主题收敛后，再统一处理历史层：

1. `plan/` 中真正历史性的材料迁入 `archive/`
2. `feature_designs/` 中已废弃方案迁入 `archive/feature_designs/`
3. 被替代的旧设计页保留 redirect 和替代说明

## 7. 与代码和数据库保持一致的机制

目录结构本身不能阻止漂移，真正能阻止漂移的是变更规则。

### 7.1 每类变更都要先指明 canonical 文档

任何需求或实现开始前，必须先回答：

1. 这次改动的 canonical 文档是哪一份？
2. 这次会影响哪个代码目录？
3. 这次会影响哪个数据库真理源？

如果答不上来，就不应该先写新文档。

### 7.2 文档更新顺序固定

推荐顺序：

1. 先改代码 / schema / migration / tests
2. 再更新 canonical 文档
3. 最后更新 quick reference、README、补充文档、AI 入口

禁止反向操作：

1. 先写一份新设计说明
2. 不回写 canonical
3. 让新说明在目录里长期悬空

### 7.3 每份 canonical 文档都必须带真理源声明

后续建议为 canonical 文档统一补充顶部元信息：

1. `Status: canonical`
2. `Code owners`
3. `Code paths`
4. `DB sources`
5. `Supersedes`
6. `Last verified against code`

这样可以显著降低“看起来很像真理源，其实已经过时”的风险。

### 7.4 引入文档生命周期状态

所有文档必须属于以下状态之一：

1. `canonical`
2. `supplementary`
3. `incubation`
4. `legacy`
5. `archive`

没有状态的文档，默认视为治理缺失。

### 7.5 建立轻量漂移检查清单

每次涉及 API / DB / 运维变更时，PR 或执行计划里至少检查：

1. SQL / migration 是否已更新
2. canonical 文档是否已更新
3. `03_Projects/` 本地开发说明是否受影响
4. `06_Reference/` 快速入口是否受影响
5. 是否还有旧文档在描述被替代行为

## 8. 后续新增功能时的落文规则

为了避免未来继续长出散点文档，新增文档遵循以下准入规则：

### 8.1 新功能文档先选层级，再建文件

新文档只能进入以下之一：

1. 平台协议：`agent/`
2. 系统边界：`02_System_Architecture/`
3. 主流程：`03_Core_Workflows/`
4. 数据结构与资金：`04_Database_Design/`
5. 运维与运行：`05_DevOps_Deployment/`
6. 快速查阅：`06_Reference/`
7. 项目本地说明：`03_Projects/<project>/`
8. 孵化方案：`feature_designs/`
9. 历史方案：`archive/`

如果不属于以上任何一层，说明主题还没有被正确建模。

### 8.2 不再向 root `docs/` 新增业务单文件

root 只接受：

1. 全局入口
2. 全局治理
3. 顶层地图

业务设计、流程说明、专题方案不再直接落到 root。

### 8.3 孵化设计必须有升级出口

进入 `feature_designs/` 的文件必须在开头声明：

1. 当前状态是 incubation
2. 对应的潜在 canonical 目标目录
3. 满足什么条件后升级

## 10. 最终结论

Synapse 当前文档体系已经具备主骨架，问题不在“完全没有结构”，而在：

1. 层级之间还存在旧内容并存
2. root 散点文件过多
3. 文档生命周期没有被制度化
4. 代码 / 数据库 / 文档的对齐机制还不够硬

因此，合理的长期方案不是推倒重来，而是：

1. 保留当前六模块 + `03_Projects/` 主骨架，并把 `agent/` 视为待拆分吸收的过渡层
2. 新增 `00_Governance/` 和统一 `archive/`
3. 把 root 散点文档逐步回收入模块
4. 把 `agent/` 逐篇并入 `00-06` 对应模块，而不是长期独立悬挂
5. 为每份文档补状态、owner、真理源声明
6. 把“新功能先找 canonical 文档，再写说明”变成强规则

只要这五条执行到位，后续功能继续增长时，文档维护复杂度会稳定下降，而不是继续线性失控。
