# 管理后台审计与合规设计

本文定义平台管理后台的审计模型、日志分类、留存策略、查询边界和合规控制要求。

目标是保证：

- 管理员的每一次关键操作都可追踪
- 审批流、执行流、资金变更能串成完整责任链
- 审计日志不会与普通业务日志混杂失真
- 后续做内部追责、复盘、对账、合规检查时有统一依据

## 1. 为什么需要单独的管理员审计体系

交易网关里已经有业务审计，但管理后台的审计要求更高，原因是后台拥有：

- 平台配置修改权
- 风控规则修改权
- 手工补账申请与审批权
- 提现、退款、高危放行审批权
- 管理员提权能力

这意味着后台日志必须回答以下问题：

1. 谁发起了这个操作
2. 谁审批了这个操作
3. 谁最终执行了这个操作
4. 改动发生前系统是什么状态
5. 改动发生后系统变成了什么状态
6. 如果结果错误，责任链条在哪一环断裂

如果没有独立的管理员审计体系，生产上会出现两个问题：

- 业务日志太杂，无法快速定位后台责任动作
- 即使发现异常，也很难分清“自动系统行为”和“人工后台操作”

## 2. 审计设计原则

### 2.1 管理审计与业务审计分离

建议分成至少两类日志：

- `admin_action_audit`：管理员控制面动作
- `finance_business_audit`：交易业务动作

二者可以关联，但不要混成一张“万能日志表”。

### 2.2 审批日志与执行日志分离

审批“通过”不代表命令“执行成功”。

因此审计上必须分开：

- 审批行为日志
- 执行行为日志

否则会出现“审批通过但执行失败”时信息混乱。

### 2.3 审计日志默认不可改

审计日志必须具备：

- append-only 语义
- 不允许普通管理员修改
- 删除操作极度受限
- 导出留痕

### 2.4 关键标识全链路可关联

所有审计记录至少应支持通过这些字段串联：

- `request_id`
- `trace_id`
- `approval_id`
- `job_id`
- `resource_type`
- `resource_id`
- `operator_id`

### 2.5 可读范围严格分级

审计日志不是所有管理员都能看全量明细。

例如：

- `support_agent` 只能看与工单相关的有限操作结果
- `finance_admin` 只能看财务相关日志
- `compliance_auditor` 才能看管理员全量行为链

## 3. 审计日志分类

建议后台至少有四类审计数据。

### 3.1 管理员动作审计 `admin_action_audit`

记录管理员在后台上的所有控制面操作，例如：

- 登录成功/失败
- 登出
- MFA 验证
- 打开某个敏感页面
- 修改平台配置
- 发起补账申请
- 审批提现申请
- 导出报表
- 授予角色

### 3.2 审批链路审计 `admin_approval_audit`

记录审批单生命周期中的动作，例如：

- 创建审批单
- 提交审批单
- 指派审批人
- 审批通过
- 审批拒绝
- 审批撤销
- 审批升级
- 审批超时

### 3.3 执行命令审计 `admin_execution_audit`

记录审批通过后的实际执行动作，例如：

- 开始 replay 某笔充值
- 执行提现放行
- 执行费率配置变更
- 执行冻结账户
- 执行失败重试

### 3.4 资金业务关联审计 `admin_finance_link_audit`

记录后台动作与交易真相之间的关联桥，例如：

- `approval_id -> tx_hash`
- `approval_id -> deposit_intent_id`
- `approval_id -> withdrawal_intent_id`
- `approval_id -> balance mutation result`

这类桥接层很重要，因为它把后台控制面和交易主真相连起来了。

## 4. 推荐审计字段

### 4.1 通用审计字段

每条后台审计建议至少包含：

- `audit_id`
- `timestamp`
- `action_type`
- `operator_id`
- `operator_email` 或 `operator_account`
- `operator_role`
- `request_id`
- `trace_id`
- `session_id`
- `client_ip`
- `user_agent`
- `resource_type`
- `resource_id`
- `result_status`
- `error_code`
- `message`

### 4.2 审批相关字段

审批类日志建议补充：

- `approval_id`
- `approval_type`
- `approval_level`
- `requester_id`
- `approver_id`
- `approval_status`
- `approval_comment`

### 4.3 资金相关字段

涉及资金动作时建议补充：

- `owner_address`
- `tx_hash`
- `event_key`
- `amount_usdc`
- `before_balance`
- `after_balance`
- `ledger_id`
- `intent_id`

### 4.4 配置变更字段

涉及配置修改时建议补充：

- `config_key`
- `before_value_json`
- `after_value_json`
- `change_reason`
- `effective_at`
- `rollback_token`

## 5. 关键操作的审计要求

### 5.1 管理员登录与会话

必须记录：

- 登录成功
- 登录失败
- MFA 成功
- MFA 失败
- 强制下线
- 密码或凭证重置

高风险要求：

- 多次失败登录自动告警
- 异地登录或非常用设备登录打标

### 5.2 补账与资金修复

必须记录：

- 谁发起补账申请
- 补账目标用户是谁
- 关联 txHash / eventKey 是什么
- 审批人是谁
- 执行结果是什么
- 修复前后余额差异是什么

如果补账失败，还必须记录失败原因和是否允许重试。

### 5.3 提现与退款审批

必须记录：

- 发起来源
- 审批结论
- 风险结论
- 金额
- 受影响账户
- 执行产物，例如 txHash

### 5.4 平台配置与费率修改

必须记录：

- before / after diff
- 谁发起
- 谁审批
- 生效时间
- 回滚标识

### 5.5 管理员提权与角色变更

必须记录：

- 被授予人
- 原角色
- 新角色
- 发起人
- 审批人
- 生效时间

该类日志建议额外抄送到安全或合规告警渠道。

## 6. 审计日志与审批流的关联方式

后台审计必须能从任意一个入口回溯整条链路。

### 6.1 以 `approval_id` 为主轴

建议大部分高危管理动作以 `approval_id` 为主轴串联：

- 申请日志
- 审批日志
- 执行日志
- 资金结果日志

### 6.2 以 `trace_id` 为技术链路主轴

一次后台操作可能跨：

- `admin-front`
- `gateway-admin`
- 内部 job worker
- `gateway`
- 数据库

建议统一传递 `trace_id`，用于技术排障。

### 6.3 以 `resource_id` 为业务对象主轴

例如：

- 某个 `deposit_intent_id`
- 某个 `withdrawal_intent_id`
- 某个 `admin_user_id`
- 某个 `config_key`

这样从业务对象也能回溯历史操作。

## 7. 留存与归档策略

建议按日志类别定义最低留存期。

### 7.1 登录与会话日志

建议：

- 热数据保留 `90` 天
- 冷归档保留 `1` 年以上

### 7.2 审批与资金相关后台日志

建议：

- 热数据保留 `180` 天
- 冷归档保留 `3 ~ 7` 年

原因：这类日志最容易涉及资金争议、内部审计和合规核查。

### 7.3 配置变更日志

建议：

- 保留期不低于 `3` 年

### 7.4 超级管理员与提权日志

建议：

- 长期归档
- 不允许普通归档任务直接删除

## 8. 查询与导出权限控制

审计日志查询必须做二次权限收缩。

### 8.1 谁可以看什么

建议：

- `support_agent`：只能看与自己工单范围相关的有限审计摘要
- `finance_admin`：看财务域相关日志
- `risk_admin`：看风控域相关日志
- `platform_ops_admin`：看系统与配置日志
- `compliance_auditor`：看全量后台日志
- `super_admin`：可看全量，但所有访问也必须被记录

### 8.2 导出必须留痕

导出审计日志时必须额外记录：

- 谁导出的
- 导出时间
- 导出过滤条件
- 导出条数
- 是否包含敏感字段

### 8.3 敏感字段脱敏

对于部分角色，查询结果应自动脱敏：

- 邮箱
- IP
- 用户标识
- 钱包地址局部脱敏
- 配置中的敏感 secret

## 9. 异常与告警策略

后台审计不仅用于事后查询，还应该用于实时异常检测。

建议至少做以下告警：

### 9.1 认证告警

- 短时间多次登录失败
- 异地登录
- 异常设备登录
- 绕过 MFA 失败尝试

### 9.2 权限告警

- 超级管理员登录
- 角色提升
- 高危权限授予
- 审计日志导出

### 9.3 资金控制告警

- 手工补账执行
- 大额补账申请
- 大额提现审批通过
- 高危白名单放行
- 手工余额调整

### 9.4 配置治理告警

- 平台费率修改
- 风控阈值修改
- 服务注册核心配置变更

## 10. 紧急通道与事后复盘

生产上一定会出现紧急操作场景，例如：

- 紧急冻结异常账户
- 紧急暂停某类提现
- 紧急回滚平台配置

建议后台保留 `emergency_action` 通道，但必须满足：

1. 有专门的紧急动作权限
2. 强制填写紧急原因
3. 自动打 `emergency=true`
4. 自动触发高优先级审计告警
5. 事后必须生成复盘单

紧急通道不是免审批通道，而是更强审计通道。

## 11. 存储与篡改防护建议

后台审计存储建议至少满足：

- append-only 逻辑
- 数据库层最小更新权限
- 对删除、清理动作单独审批
- 归档文件带完整性校验

更进一步的方案可以做：

- 审计归档 hash 链
- 对象存储 WORM 策略
- 定期快照封存

## 12. 与 `gateway` 审计的关系

建议边界如下：

- `gateway` 继续记录交易与系统运行审计
- `gateway-admin` 记录后台控制面审计
- 两边通过 `trace_id / approval_id / tx_hash / intent_id` 关联

也就是说：

- `gateway` 负责记录“钱怎么变了”
- `gateway-admin` 负责记录“是谁批准让它变的”

这两个维度都必须存在。

## 13. 第一阶段最小落地要求

如果先做第一期，最少要实现：

1. 管理员登录与 MFA 审计
2. 审批单生命周期审计
3. 补账 / 提现 / 退款 / 费率变更四类关键动作审计
4. 审计日志按角色限权查询
5. 审计日志导出留痕

## 14. 最终建议

1. 管理后台必须有独立的管理员审计体系，不能只依赖交易网关现有日志。
2. 审批日志、执行日志、资金真相日志必须可关联，但不要混成一个模糊大表。
3. 所有高危动作必须默认告警，所有导出必须留痕。
4. 超管操作、提权操作、手工补账操作要作为最高敏感审计对象。
5. 第一阶段先把补账、提现、退款、费率变更四类审计链路做完整，再扩展到其他管理动作。
